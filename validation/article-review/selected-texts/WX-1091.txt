#  Pi Harness V2 ：可恢复的 Agent 运行时

现在做一个“能调用工具的 Agent”，已经不算特别难。

真正难的是另一组问题：模型请求发到一半，进程崩了怎么办？工具已经执行，但结果还没写回怎么办？用户在工具运行时改变方向，这条消息该进当前回合还是下一个回合？恢复之后，怎么证明没有重复执行、没有丢消息，也没有把一笔已经发生的模型费用算没？

Pi 仓库里的《Durable AgentHarness design》，正面回答的就是这些问题。

这不是一篇常规产品介绍，而是一份超过 3000 行的工程设计规范。它把 Session、并行
Lane、操作日志、工具重放、上下文压缩、延迟请求、Hooks、Telemetry 和崩溃测试连成了一套完整协议。

它提出的标准很硬：  ** 一个 Prompt 一旦被接受，就成为持久化操作。进程崩溃后，新进程必须能从最后一个安全边界恢复；任何崩溃状态都必须可处理。
**

🔶 核心判断

Agent Harness 的价值，不只是让模型持续调用工具，而是把每一次模型请求、工具执行、状态变更和用户输入，都变成可以解释、恢复和验证的运行事实。

PART 01

##  一、从“能跑”到“跑不丢”，中间差了一套运行协议

  

普通 Agent Loop 通常围绕一条主线展开：把消息发给模型，发现工具调用就执行工具，再把结果塞回上下文，直到模型停止。

这条循环在 Demo 里足够好用，但一旦进入长任务和真实业务，问题马上出现。

●  模型调用失败后，重试次数是否会因为重启而清零？

●  工具已经产生外部副作用，但本地还没记录结果，恢复时能不能再跑？

●  中途收到的 steering、follow-up 和配置修改，谁应该被保留，谁应该在 abort 后取消？

●  两个并行任务共享一段历史时，如何避免复制整份上下文？

●  断线重连后，客户端从哪里获得一致状态？

Harness V2 把一次运行定义为  ** Operation  ** 。Prompt、压缩和导航都属于持久化操作：先被接受并记录，再开始执行，最后以
` completed  ` 、  ` failed  ` 、  ` aborted  ` 或特定结构操作可用的  ` declined  ` 结束。

这里最重要的变化是：  ** 运行过程不再只是内存里的控制流，而是有持久化语义的状态机。  **

文档也主动承认了做不到的边界。比如，Hook 自己发出的 HTTP 请求或文件写入，Harness 看不到，因此无法保证 exactly-
once；需要崩溃安全的 Hook，必须使用 operation id 等稳定标识自行实现幂等。流式模型响应的半成品也不持久化：中断后只能重试或放弃。只有
Deferred Request 返回的 Handle 会被当作持久化事实，恢复时继续领取结果，而不是重新付费发起请求。

这类边界声明很重要。可靠系统不是承诺“一切都不会重复”，而是准确指出：  ** 哪些副作用由 Harness 负责，哪些必须由外部系统幂等兜底。  **

PART 02

##  二、一个 Session 被拆成四层，各自只负责一件事

  

Harness V2 没有把所有状态塞进一条消息历史，而是把 Session 拆成四个部分。

Session 的四类持久状态

✅  ** Tree  ** ：真正的对话内容，包括消息、模型与工具配置变化、压缩摘要、分支摘要和自定义条目；只追加，不修改、不删除

✅  ** Lanes  ** ：不同工作流在对话树上的当前位置；每个 Lane 拥有自己的叶子节点，同一 Lane 同时最多运行一个 Operation

✅  ** Lane operation logs  ** ：记录已经发生什么、接下来必须发生什么，是崩溃恢复的依据，但不会进入模型上下文

✅  ** Global facts  ** ：会话名称、条目标签等 Session 级事实，以最新写入为准，同时保留追加式历史

所有写入共享一个单调递增的序号，但它们的职责被刻意隔离。

Tree 只保存“对话是什么”，Operation Log 只保存“执行到了哪里”。即使删除全部 Operation Log，Tree
仍然是一棵完整有效的对话树；反过来，恢复逻辑也不会把执行记录混进 Prompt、Transcript 或分支查询。

Lane 则解决了并行工作的问题。

它很像 Git 分支与 Worktree 的结合：一个名字指向树上的某个位置，新条目沿着自己的叶子继续生长；两个 Lane
可以共享历史前缀，然后自然分叉。每个 Lane 内部串行执行 Operation，不同 Lane 可以并行运行，而整个 Session 仍由一个
Harness 作为单写入者维护。

这比“复制一份消息数组给子任务”更干净。共享历史只存在一份，执行队列和恢复状态却彼此隔离。Slack 的一个频道可以对应一个 Session，每条
Thread 对应一个 Lane；子 Agent 也可以选择在父 Session 的新 Lane 上工作，或者 Fork 成一个完全隔离的新
Session。

Fork 的边界同样清晰：它复制条目和必要事实，不复制 Operation Log、队列和成本账本。因此 Fork 出来的 Lane 一律从 idle
开始，Token 与成本统计从零计算，但被复制消息原有的 usage 快照仍可展示。

PART 03

##  三、真正的耐久性规则：副作用之前，先写意图

  

整份设计最关键的一句话是：

“

在一个副作用发生之前，先写入一条 Intent Record，明确即将发生什么，以及它将产生哪些 ID；副作用完成后，再用这些预分配 ID 追加结果
Entry。

— Pi Harness V2 设计文档 · Durability rule

这条规则把崩溃恢复变成了可判定问题。

STEP 1  先接受操作

` operation_started  ` 记录 Operation 类型、起始叶子、原始 Prompt、首批消息和预分配
ID。调用方只有在这条记录持久化后，才算真正得到“已接受”。

STEP 2  每次尝试先留痕

模型步骤先写  ` step_attempt  ` ，工具执行先写  ` tool_started  ` 。记录中包含 attempt
次数、工具参数、回放策略和结果 Entry 的预分配 ID。

STEP 3  副作用完成后追加结果

模型响应、工具结果或错误以对应 ID 写入 Tree。恢复时，某个 Intent 是否完成，只需要检查那个 ID 的结果 Entry 是否存在。

STEP 4  根据副作用类型决定恢复动作

未完成的模型 Step 可以继续重试；未完成的工具调用只有在“当时声明可安全回放”且“当前工具仍声明可安全回放”时才重跑，否则写入一个  `
interrupted  ` 的合成结果。

这个双重回放判断很克制。

系统不能因为工具今天被标记为安全，就假装昨天那次调用也安全；也不能因为历史记录写着 safe，就忽略工具实现后来已经改变。只有历史声明和当前声明同时为
safe，恢复才允许重新执行。

模型重试也不是简单的内存计数。每一次 attempt 都是持久记录，因此“崩溃—重启—再崩溃”不会把重试次数重置成 1。模型请求一旦结算，usage
会先于分类、重试或丢弃被写进独立账本。即使某个溢出响应从未进入对话树，它已经产生的成本仍然可追踪。

上下文溢出同样被限定在一个有界流程里：若响应被判定为上下文压力导致的可恢复  ` length  ` 或 overflow 错误，Harness
会丢弃这次响应，执行一次压缩并重试；同一条用户输入最多只允许一次这类恢复，避免陷入无限“压缩—重试”循环。

PART 04

##  四、并行不靠运气：每一场竞态都只有两种合法顺序

  

耐久性之外，Harness V2 还在解决另一个更隐蔽的问题：并发调用里的 check-then-act。

例如，Agent 正准备结束当前 Run，用户恰好发来一条 steering。结果应该是哪一个？

●  steering 先提交：Run 不能结束，下一轮必须消费它；

●  finish 先提交：Lane 已经 idle，steering 返回  ` NoActiveRun  ` ，不产生写入。

系统不能出现第三种状态：结束记录已经写了，但 steering 又悄悄落进这个 Run。

为此，每个 Lane 都有一条本地的 Mutation Line。所有依赖 Lane 当前状态的决策，都必须在这条 FIFO
上完成：读取最新状态、最多提交一次持久写入、更新内存状态。模型调用、工具执行、Hook 和退避等待不占用这条线；它们可以并行运行，但最终提交必须重新校验。

文档列出了 12 类需要明确顺序的竞态，包括 prompt 对 prompt、steering 对 finish、abort 对工具执行、nextRun
对新 Run 接受、队列取消对消费，以及跨 Lane 写入。每一类都要求测试两种合法先后顺序。

更特别的是它的  ` drive: "manual"  ` 模式。

生产模式里，所有 Effect 正常执行；手动模式里，每一次持久写入、模型请求、工具执行、Hook、计时器都会先停在 Gate 前。测试可以逐个释放
Action，在任意边界关闭 Harness，再重新打开同一后端并调用  ` resume()  ` 。

这让“崩溃测试”不再依赖随机杀进程，而变成一套可机械遍历的实验：

手动驱动需要证明的事实

✅  停在某个 Action 前时，系统没有偷偷发生存储写入、模型请求或工具调用

✅  每次只释放当前看到的一个 Action，不会跨过第二个边界

✅  在每个持久化前缀上关闭并重开，都能得到可恢复状态

✅  相同脚本下，automatic 与 manual 模式产生相同的持久日志和最终结果

✅  恢复完成后，由存储重新归约出的 LaneState 必须与运行时状态完全一致

这套方法真正把“可恢复”从架构口号变成了测试对象。

PART 05

##  五、上下文、事件、Hook 和遥测，不能混成一条总线

  

很多 Agent 系统最后会变得难以维护，是因为几类信息共用了一套机制：UI 用事件流改执行，插件用日志注入上下文，Telemetry 又承担恢复状态。

Harness V2 明确把它们拆开。

●  ** Events  ** 是被动观察，供 UI 和扩展看见运行过程，不能改变执行；客户端先拿原子 Snapshot，再接实时事件，断线后重新拿
Snapshot，而不是要求服务端回放事件。

●  ** Hooks  ** 可以拦截并改变执行，例如修改上下文、请求参数、工具参数、运行边界或压缩结果；Hook 失败必须按每类 Hook 的规则隔离或
fail closed。

●  ** Telemetry  ** 只服务进程内诊断，不进入持久化状态，不参与恢复，也不替代 Events；父子 Span 通过显式参数传递，不依赖
Node 专属的全局上下文机制。

这种分层还延伸到了上下文管理。

同一 Lane 连续请求时，Provider Context 原则上只能在尾部增长，避免在旧消息中间插入内容，破坏 KV Cache。Steering
和延迟写入会等到 Checkpoint 再追加；Compaction 是唯一允许主动打破前缀缓存的操作，因为它用一次缓存失效换取更短上下文。

换句话说，Harness V2 不把“上下文压缩”当成一段摘要 Prompt，而是把它当成有触发条件、持久记录、失败路径和恢复语义的结构操作。

PART 06

##  六、它最值得学的，不是 API，而是工程验收标准

  

截至该分支 2026 年 8 月 7 日的提交，文档末尾仍列着大量未完成工作包。JSONL 格式 4 的部分仓储工作和 Telemetry
基础已经标为完成，但 Lane 集成、完整 Run 执行、工具恢复、压缩、导航、运行时遥测和最终审计等主链路，仍有不少项目处于待实现状态。

所以，更准确的理解是：  ** 这是一份正在实施的 Harness V2 规范，不是一份“全部功能已经上线”的发布公告。  **

但它已经给出了非常有价值的工程判断。

🔶 对 Agent 团队最重要的启发

不要只问 Agent
能不能完成一次任务。还要问：输入何时算被接受，副作用何时算被记录，崩溃后从哪里恢复，重复执行由谁兜底，成本如何追踪，竞态如何穷举，以及测试能否停在每一个真实
Effect 前。

如果你的 Agent 只处理一次性的低风险问答，未必需要照搬整套设计。

但只要任务会持续几分钟以上，会写文件、调用外部服务、产生费用、接收中途纠正，或者需要在崩溃后继续，那么耐久性就不再是存一份聊天记录那么简单。

真正需要掌握的是运行契约：什么是事实，什么是意图；什么进入对话树，什么只属于执行日志；哪些动作可以回放，哪些只能合成失败；哪些状态由快照重建，哪些副作用必须依赖业务系统幂等。

模型能力还会继续提高，工具协议也会不断变化。但一个长期运行的 Agent 能否进入生产，最终仍取决于这些看起来“不聪明”的基础设施。

** 会调用工具，只说明 Agent 能工作。崩溃后还能把工作接回来，才说明它开始成为系统。  **
