当 AI Agent 大规模走进研发工作流，代码生成早已不是最大瓶颈。真正困住团队的，是信任与验证。阿里开源项目 Better Harness，跳出 “做大模型” 的思路，从 Agent 工作闭环入手，给出一套治理思路。AI Agent 的下半场，比拼的不再是模型本身，而是一套成熟的工作系统。
过去一年，企业聊 AI Agent，话题总绕不开模型选型：用什么大模型、上下文窗口多大、接入多少 MCP 协议、配置多少 Skill 能力。
可当 Agent 真正落地到真实研发流程，现实问题立刻浮现： Agent 十分钟就能完成一轮代码改动，人类却要花费两小时，反复核对它是否曲解需求、绕过开发规范、遗漏测试用例，给业务埋下隐性风险。
代码产出速度变快了，但瓶颈只是发生转移 —— 从生成代码变成了校验代码。
阿里开源的 Better Harness，瞄准的正是这一痛点。它不追求把模型变的更聪明，而是审视 Agent 整套工作方式：目标是否清晰、执行过程是否可控、结果能否被验证、交付是否可靠、过往经验能不能复用。
这也释放出一个关键信号：AI Agent 的竞争，正在从模型能力竞赛，转向工作系统的较量。

一、生成不再稀缺，信任才是生产力的核心瓶颈

传统软件研发里，产出代码是稀缺资源。需求排期、开发人力、工程师时间，直接决定产品迭代快慢。
AI Agent 彻底改写了这个前提。 代码快速生成、自动化补充测试、即时输出文档，同一个需求还可以交给多个 Agent 并行处理，产能被大幅释放。但产能暴涨，不等于团队生产力同步提升。
企业需要的从来不是更多代码，而是可信的产出结果。
AI 时代，我们可以重新理解团队实际生产力公式：
实际生产力 = 生成速度 × 首次正确率 × 可验证性 × 经验复用率
Agent 生成再快，如果每一次输出都需要人工全盘复核；任务显示完成，却拿不出证据证明结果正确；同类错误反复上演，效率红利就会被审查、返工、风险成本全部吞噬。
Better Harness 的价值，就是把关注点从 “Agent 能不能干活”，升级为核心拷问：团队凭什么相信它干对了？

二、不校验最终结果，而是审计 Agent 完整工作闭环

绝大多数代码审查工具，焦点都落在最终产物：代码是否符合编码规范、测试是否跑通、有无安全漏洞。
Better Harness 与众不同，它重点审视结果产生的全过程，回答五大核心问题：

Agent 是否读懂任务，清晰知晓完成标准？

是否按照团队认可、可复现的路径执行任务？

是否留存充足证据，证明业务变更真实有效？

是否为了效率，绕过审查、审批等交付保障机制？

本次暴露的问题，能否沉淀经验服务下一轮任务？
这套逻辑不只适用于编码 Agent，几乎覆盖全部企业级 Agent 场景。 客服 Agent 有没有读懂用户诉求？营销 Agent 是否恪守品牌合规？数据分析 Agent 是否标注数据来源与计算口径？采购 Agent 是否在授权边界内做决策？
场景千差万别，底层治理逻辑相通：不只看交付了什么，更要看它是如何得到这份结果。
项目还有一个很关键的设计原则：没有观测到完整行为，不轻易判定结果好坏，直接标记为证据不足。
企业评估 Agent 时，很容易陷入虚假确定性：测试通过就等同于任务落地成功；配置规则就默认 Agent 必然遵守；产出报告就代表过程可追溯。 但 “存在机制”≠“机制被执行”，“检查通过”≠“业务结果正确”。 Better Harness 本质是一套工作过程审计与优化系统，绝非简单的打分报表。

三、成熟 Agent 系统，前馈约束与反馈校验缺一不可

Better Harness 底层核心逻辑，可以总结为：前馈 + 反馈。
前馈：发生在 Agent 行动之前。任务说明、产品规范、项目约束、可用工具、操作边界、验收标准，提前告知 Agent：什么该做、什么禁止做，什么样的输出才算合格。
反馈：发生在 Agent 执行之后。单元测试、代码巡检、运行日志、钩子机制、自动评审、人工审批，观测 Agent 实际表现，定位问题，驱动修正。
只做前馈、缺少反馈：团队堆砌越来越多规则文档，但无法确认 Agent 是否真的落地执行，最终变成一份无人兑现的说明书。 只做反馈、缺少前馈：依靠不断试错纠错，同类问题循环反复出现，治理永远在 “事后救火”。
一套健康的 Agent 工作闭环应当是：明确意图 — 约束执行 — 获取信号 — 修正结果 — 沉淀经验
这也说明，Prompt 远远不是 Agent 管理的终点。 Prompt 仅能表达单次任务意图；Harness 则把任务目标、权限边界、执行路径、验收证据、复盘学习，组合成一套持续运转的完整系统。

四、产品经理新命题：从写需求，到设计 Agent 工作制度

Better Harness 起源于编码 Agent，但对产品经理的启发更为深远。 当 Agent 承接大量具体工作，产品经理设计的不再只有产品功能，还要设计 Agent 的整套工作制度。
1、从撰写 PRD，升级拟定 “证据合同”
过去写需求，重点描述要实现什么功能。面对 Agent，仅有功能描述远远不够。 需要额外定义：

核心目标，以及明确不在本次范围的事项

Agent 可访问的数据、可调用工具

哪些动作自动执行，哪些必须人工确认

任务完成，必须提交哪些佐证材料

出现哪些状况，任务必须终止、回滚
核心问题不再是 “需求写没写清楚”，而是：当 Agent 汇报任务完成，需要拿出什么证据，我才能够信任？这就是产品与 Agent 之间的「证据合同」。
2、放弃极致全自动化，落地分级自治
很多企业评判 Agent，看它替代多少人工步骤。但完全自动化未必是最优解。 更务实的思路，基于风险划分自治等级：

低风险、可逆向任务：自动执行 + 自动校验

中等风险任务：Agent 完成执行，交付前人工复核确认

高风险、不可逆、强合规任务：收紧 Agent 操作权限，保留人类最终决策权
Agent 治理，目标不是让人彻底退场，而是把人的精力释放到需要权衡、判断、承担责任的环节。我们追求的不是最大程度自治，而是安全、可验证前提下的最大化自治。
3、告别聊天记录存档，沉淀组织级能力
现在很多团队使用 Agent，依旧停留在个人使用层面。 A 员工手动修正 Agent 错误，B 员工遇到同类问题要重新踩坑；优质执行路径只留在对话记录；Agent 犯下的错误人工修复完毕，却不会作用于下一次任务。
有价值的经验，不能沉睡在聊天会话里，要转化为规则、Skill、模板、测试用例、检查器、审批节点。 建立一条简单改进原则： 第一次出错可以是偶然；重复发生的错误，就是系统层面的缺陷。 每一次重复 bug，都要补充前馈指引，或是新增自动检测的反馈传感器。 让 Agent 做完当前任务的同时，持续迭代团队未来的做事方式。

五、企业 AI 护城河：不在于模型，而在于 Harness

大模型能力正在快速普惠。 同款模型各家都可以接入，现成 Agent 产品也能够采购。单纯依靠模型，很难构筑长期差异化壁垒。
但 Harness 不一样。 它承载企业独有的业务规则、决策边界、质量标准、审批流程、历史业务经验，这些是外部无法直接复制的资产。
未来企业 Agent 综合能力，由三类资产共同构成：
模型
：提供通用理解、内容生成的基础能力
工具
：赋予访问数据、操作系统的能力
Harness
：沉淀企业专属工作模式与纠错闭环
打个比方：模型是汽车发动机，Harness 就是道路、仪表盘、防护护栏、整套运维保障体系。 发动机决定车辆理论极速；Harness 决定车辆能不能稳定、安全抵达终点。
企业 AI 转型，不是批量采购 Agent 账号，而是把员工脑海中的隐性业务经验，转变为机器可读、可执行、可校验的组织系统。 越早完成这一步，越能把 Agent 从个人效率工具，升级成企业生产力基础设施。

六、理性看待：Better Harness 并非万能解药

Better Harness 指明了极具价值的方向，但不能把它当成 Agent 治理的终极答案。
第一，证据充分 ≠ 业务方向正确。 测试通过仅代表满足测试用例；流程完整仅代表 Agent 走完流程。它无法自动证明我们解决的是真正有价值的业务问题，也不能保证用户愿意使用最终产出。涉及用户体验、商业权衡、复杂业务取舍，人的判断依旧无可替代。
第二，评分体系存在被 “策略性优化” 的风险。 一旦 Harness 报告分数绑定绩效考核，团队就会追求报表好看，而非真正降低业务风险。出现测试越堆越多、文档愈发完备，但业务实际收益毫无改善的局面。 不必执着单次报告绝对分数，重点观测长期指标变化：返工率下降、人工审查耗时缩短、重复错误持续减少。
第三，Harness 自身也会产生技术债务。 规则会过期失效，Skill 互相冲突，检测器频繁误报，过度约束会扼杀 Agent 处理特殊场景的灵活性。 Harness 不是配置一次就一劳永逸的静态制度，它需要专门负责人、版本管理、定期清理迭代，是一套需要持续运营的产品。

七、产品团队落地起步：从小规模试验开始

不用一上来搭建庞大完整的 Agent 治理平台，优先挑选高频、边界清晰、结果可验证的小任务试点。 例如：缺陷修复、数据周报生成、用户反馈整理、标准化运营配置。
围绕试点任务，搭建四项最小资产：
任务卡
：明确目标、排除项、约束条件、验收标准
受控路径
：限定 Agent 可用工具、数据访问范围、操作权限
结果证据集
：强制输出测试报告、数据来源、变更记录、验收凭证
学习规则
：重复出现的问题，必须转化为新指引或自动检查机制
持续运行多轮任务，重点跟踪四项核心指标：一次通过率、人工审查耗时、重复错误率、问题定位耗时。 指标持续向好，就代表团队搭建的不是一个复杂 Agent，而是一套具备自我学习能力的工作系统。

写在最后
Better Harness 最值得借鉴的，不是一份 Agent 评估报表，而是它重新定义了 Agent 的管理范式。
过去企业管理对象是人、岗位、业务流程；未来，我们还要管理人、Agent、工具、规则、反馈共同组成的复杂闭环。 产品经理也迎来新职责：不止设计用户怎么使用产品，还要设计 Agent 如何理解目标、执行任务、自证结果、沉淀经验。
下一阶段领先的企业，未必是 Agent 使用数量最多的企业。而是更早把不确定性转化为可核验证据、把重复错误转化成系统能力的团队。
模型划定 Agent 能力上限；Harness 决定这份能力，能不能转化为稳定可靠的组织生产力。
