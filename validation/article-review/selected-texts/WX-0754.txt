算是做了一次大版本更新，主要是强“数据底座”、稳“Harness框架”、增“RSI思想”。V0.05版本更新比较慢，一是最近太忙了；二是做了一些软件基础性工作和前沿探索；三是因为codex的5小时额度限制又回来了。最近会收到一些留言或私聊，有部分提出质疑或是看不起AI
coding，认为你这个东西就是AI编的，一堆屎山代码，没有价值。其实我的观点是AI是工具，是一种高效的工具，可以增强人，放大人的能力，但是前提是你得有能力，然后才能放大。所以AI越强大越需要人的判断能力。其实这也是事物发展的规律，当一件事情开始被大家关注时，一定会出现不同声音，所以我也很愿意和各位大佬去讨论问题，思想的碰撞，给我更多灵感。我做动态本体这个专题的初衷，其实是通过自己技术试验和场景实验来解答我自己的疑虑。长久以来，我对动态本体的态度始终是保持克制的，不过度渲染，也不武断否定，我也在不同场景表达我的观点“动态本体不是唯一解决方案”，我只是想通过技术来客观看待动态本体这个概念。感谢大家的关注、阅读、转发和留言，“
动态本体 + 本体 MCP：把 OpenClaw接入东海 ADIZ 空情研判的 MVP 实战
”这篇文章已经突破1万阅读量了，我也希望可以和更多的业界大佬一起讨论问题。在这个过程中我也欣然结识很多志同道合的伙伴，我们在智能化这条道路上“共赴刀山、火海、春秋、冬夏”。
前几版做下来，我们已经有了一个能跑起来的动态本体 MVP：页面上有东海防空识别区，有空中目标，有航迹，有 DeepSeek Harness
的任务入口，也有本体函数给出的概率研判和预警机阵位规划。这个阶段最容易让人兴奋，因为地图动起来了，目标点会走，输入一句话能出一份结果，客户也能很快理解系统大概在干什么。
但真正做演示、做联调、做业务复盘时，很快会遇到另一个问题：系统不是只要“这次给出答案”就够了。它还必须记得这次为什么这么判，哪些地方判错了，哪些地方不稳定，哪些规则需要调整，哪些
Skill 值得升级，哪些结论必须人工复核。否则每次演示都像从零开始，今天踩过的坑，明天还会再踩一遍。  所以V0.05
这版，我们没有继续堆更多按钮，也没有单纯增加更多目标，而是把重点转向三个更底层的能力：RSI 闭环、三层记忆和轻量 Foundry
数据底座。简单说，就是让系统从“能做一次研判”，往“能把每次研判变成下一次改进依据”走一步。  

PART 01

  
为什么要做 RSI 闭环  
  
我们这里说的RSI，不是让系统自己偷偷改代码、自己上线、自己替代人做高风险决策。这个边界必须讲清楚。当前系统里的
RSI，更准确地说是“动态本体递归自我优化闭环”：系统在任务运行后，把问题、证据、改进建议、验证结果和人工复核结论结构化保存下来，再作为下一轮任务的输入。
比如我们前面遇到过几个很典型的问题。目标刚开始播放时，早期航迹点不足，某些目标进入 ADIZ
的概率一度偏高；后来随着更多航迹点流入，概率又迅速回落。这说明模型在短窗口下过度自信。再比如预警机阵位规划，单架预警机时可以从多个候选阵位里选最优，但多架预警机不能简单取“第一名、第二名、第三名”，因为多机之间有覆盖重叠、任务分区、互补补盲和敌方防空规避问题。还有
DeepSeek Harness 与 MCP 交互时，偶发出现后端失败、非 JSON 输出、前端兜底逻辑绕过 Agent
等问题，这些都不是一句“修好了”就应该结束的事。  RSI
闭环要做的，就是把这些问题变成可管理的改进对象。系统发现“早期概率跳变”后，不是只在聊天里提醒一句，而是生成一个 Improvement
Task；发现“双预警机规划不应该按单机排名直接取前两名”，就把它写成候选优化；发现“工具调用失败后不能静默回退到本地假结果”，就把它固化为 Harness
层的运行边界。后面再通过 baseline 对比、回放验证和人工晋级，决定它能不能进入下一版。  这就是我们当前 RSI
的定位：它不是模型自我觉醒，而是系统把业务经验变成可复盘、可验证、可升级的工程闭环。

PART 02

  
三层记忆：让经验有地方可去  
  
如果只说“系统要有记忆”，其实很容易变成一句空话。我们这次把记忆拆成三层：热记忆、温记忆、冷记忆。  
  
热记忆  热记忆最贴近当前任务。比如这一轮正在研判哪些目标，当前选中了哪个目标，DeepSeek Harness
调用了哪些本体工具，本轮有没有生成预警机规划，有哪些复核项尚未处理。这类信息生命周期很短，任务结束后不一定全部保留，但它对当前 Agent 判断很重要。  
  
温记忆
温记忆保存的是场景经验。它不像热记忆那么临时，也不像本体规则那么稳定。比如“早期航迹点不足时，概率不要过早给高置信结论”“多预警机阵位要联合优化，不能按单机排序直接分配”“敌方水面防空力量会影响预警机安全阵位选择”，这些都是在多轮任务中反复出现的经验。它们适合被召回，也适合后续变成改进建议。  
  
冷记忆  冷记忆则是稳定知识。这里放的是本体结构、对象定义、Link 关系、函数链、Skill
说明、治理边界和高风险动作门控。冷记忆不是每次任务都改，它更像系统的长期业务骨架。只有经过复核、验证和版本晋级的内容，才应该沉淀到这一层。
这三层记忆还有一个重要原则，叫“经济遗忘”。低价值内容不应该无限堆积，也不应该被静默删除。热记忆可以压缩成摘要，温记忆可以按场景归档，冷记忆只保留通过复核的稳定知识。这样做的好处是，系统不会越用越乱，而是把真正有价值的经验留下来，把噪声压缩掉。
这也是我们为什么单独做了三层记忆看板。业务人员不需要关心底层 JSON
怎么写，只要能看到：当前任务记住了什么、哪些经验被复用、哪些本体知识已经稳定、哪些记忆可以被 Agent 在下一轮召回。

PART 03

  
Foundry 增强：先把数据底座做实  
  
如果没有数据底座，本体很容易变成漂亮的图。对象画得再好，最后还是要回答一个朴素问题：这些属性从哪里来？目标的速度、航向、高度来自哪张表？情报置信度来自哪份报文？预警机规划用到的雷达、盲区、敌方水面防空力量，是不是有可追溯的数据来源？
这次我们把数据底座往 Foundry 方向推进了一步。不是上来就做一套庞大的平台，而是先做一个轻量可运行版本：MinIO/S3 负责对象存储，Parquet
负责列式数据文件，DuckDB 负责本地查询和分析。本体运行时不再只依赖内嵌样例，而是可以通过Lakehouse API 查询语义表。
当前数据大体分成两层。raw 层保存原始来源，例如态势数据、航侦报文、技侦报文、开源地理和历史案例；semantic层把这些数据整理成业务可用的表，例如
air  _ targets、track  _ points、intel  _ reports、airspace  _ zones、ground  _
radar  _ sites、enemy  _ surface  _ air  _ defense、awacs  _ assets 和 context  _
graph  _ memory。
这一步的意义很实际。过去前端如果显示一个目标，别人会问“这个点是不是写死的”。现在我们可以说，目标航迹来自语义航迹表，播放时按 step
查询；如果查询失败，系统停止播放并提示，不再偷偷用旧数据顶上。过去如果研判结果不对，很难追到源头；现在至少可以沿着表、字段、记录和本体对象的映射往回查。
这就是我们说的最小可运行 Foundry：它还不是完整工业级数据平台，但已经具备“数据可接入、对象可建模、计算可调用、结果可追溯”的骨架。  

PART 04

  
多预警机规划开始走向“运筹问题”  
  
预警机阵位规划是最近变化比较明显的一块。早期版本里，我们能给出一个 KJ-2000
的阵位，并在地图上显示起飞机场、值班阵位和跑道形巡逻航线。后来加入双机、多机需求后，问题复杂度立刻上来了。
单机规划关注的是“这个阵位好不好”。多机规划关注的是“一组阵位合起来好不好”。这两个问题不是一回事。一个阵位单独看评分很高，但如果两架预警机的覆盖区高度重叠，联合效果可能并不好；一个阵位单独评分一般，但如果能补上陆基雷达盲区、避开敌方水面防空火力，又和其他预警机形成互补，它在组合里反而有价值。
所以当前版本把预警机规划从简单排序推进到组合优化思路。它要同时考虑 ADIZ
覆盖率、雷达盲区补盲率、敌方水面防空规避、平台间隔、航线周期、燃料余量和值班半径。后续如果接入运筹大模型或兵棋系统，预警机规划本体可以继续扩展：模型负责生成更强候选方案，兵棋系统负责回放检验效果，RSI
闭环负责把效果差异写回版本仓库和记忆系统。
这里最值得强调的是：本体不是只管“空中目标”，也可以把“预警机阵位方案”变成决策对象。目标进入概率是上游输入，预警机规划是下游决策，两者通过本体 Link
串起来。这样业务链条就从“看目标”走到了“给方案”。  

PART 05

  
版本仓库：让每次进化都能追溯  
  
做 RSI闭环时，我们还补了一块很关键的东西：版本仓库。因为系统如果会改进，就必须能回答三个问题：改了什么，为什么改，改完比以前好不好。
现在版本仓库里不只放一个当前版本，还要显示 baseline、candidate、comparison和 promotion record。baseline
是旧版本能力水平，candidate 是候选改进，comparison 是新旧对比，promotion record
是晋级或驳回记录。每个可迭代对象都需要有版本号、日期、修改权限、修改人、复核人和状态。
这套机制的业务意义是容错。候选版本不直接覆盖稳定版本，必须先在固定场景下回放验证。如果效果变好，而且没有突破安全边界，再进入人工复核；如果效果不好，就保留为失败经验，或者回滚。这样系统可以持续学习，但不会失控。
未来可迭代的对象会越来越多。除了本体模型和 Skill，记忆文档、Context Graph、规则配置、模型参数、报告模板、MCP
调用流程、外部系统适配器，都可以进入版本仓库。换句话说，RSI 不只是“改模型”，也包括改产出物、改工具链、改记忆、改本体。

PART 06

  
这版真正改变了什么  
  
如果用一句话总结 V0.05：我们把系统从“单次研判演示”推进到了“可沉淀、可复盘、可迭代”的方向。
研判台依然是业务入口，用户能看到地图、目标、航迹、概率和预警机规划；动态本体构建工具继续承担业务建模入口，让新场景可以被构建成本体；RSI
页面则成为系统成长入口，把问题、改进、baseline、版本和人工复核串起来。三层记忆让经验有地方沉淀，Foundry
数据底座让对象有数据来源，版本仓库让改进可追溯，DeepSeek Harness 让自然语言任务能够进入本体工具链。
这几件事合在一起，系统的味道就变了。它不再只是一个“会回答”的智能体，也不只是一个“会显示”的态势页面，而是在向一个业务可治理的智能系统靠近：它知道数据从哪来，知道对象是什么，知道函数怎么调用，知道决策怎么写回，也知道自己哪些地方还需要复核和改进。  

PART 07

  
下一步  
  
下一步最重要的不是继续堆更多图标，而是把“真实可用”继续做深。

  1. 开放任务适配要继续强化。单架、双架、三架预警机规划必须由用户指令驱动，后端重新解算，前端只负责展示结果，不能写死数量和模板。 
  2. 三层记忆要从看板走向真实闭环。研判结束后，热记忆应自动更新；人工复核后，关键经验应进入温记忆；稳定规则和本体约束应进入冷记忆。后续 DeepSeek Harness 再做任务时，要能主动召回这些记忆。 
  3. Foundry数据底座要继续补齐。现在已经有 MinIO/S3、Parquet和 DuckDB 的轻量形态，后面需要进一步完善数据质量检查、字段级 lineage、数据版本和任务回放数据集。 
  4. RSI的评估机制要更硬。每一个候选改进都应该能和 baseline 做对比，能说明收益、风险和适用边界。没有通过回放验证和人工门控的内容，不能进入稳定版本。 
  5. 外部系统要开始预留接口。未来接入运筹大模型和“鱼叉”兵棋系统后，系统就可以形成更完整的闭环：动态本体提出方案，运筹模型优化方案，兵棋系统检验方案，Context Graph 记录结果，RSI 再推动下一轮优化。 

到这一步，动态本体 MVP 的方向就更清楚了：它不是做一个漂亮页面，也不是做一个孤立
Agent，而是做一套能把数据、业务、智能体、模型、记忆和复盘机制连接起来的最小可运行智能底座。
