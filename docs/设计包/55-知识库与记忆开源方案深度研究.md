# 知识库、文档工作空间与记忆：最新开源方案深度研究

研究日期：2026-09-11。状态：研究结论与候选建议，`NOT_IMPLEMENTED / RELEASE_NOT_CLEARED`。配套实施设计见[56号](56-知识记忆技术栈与实施决策.md)。

## 1. 结论与本次修正

此前41号明确了知识、记忆和权限原则，36号核过底座，但还不足以回答“哪套知识与记忆方案最适合整个产品”。本次补充一手文档、固定源码、依赖、发行和许可核查。没有依据可以声称某个产品在所有场景下都是最佳。

**本项目推荐实践是：文档作为人和数字员工共同理解、编辑和交付的载体；由现有业务服务管理归属、权限、版本和发布；检索索引与记忆摘要作为可重建的派生层。** 按业务实例隔离运行工作区，按项目/人员/团队作用域维护长期知识与经验，采用按需读取与检索结合的方式。无需让普通员工理解向量库、图数据库或记忆框架。

在36号“RuoYi-AI合格社区子集优先POC”的条件下，首选组合为：

| 职责 | 优先组件或机制 | 边界 |
|---|---|---|
| 文档、任务资料、产物 | 底座文件服务、不可变内容版本、现有关系数据库 | 文档正文与元数据各有单一权威；工作目录是受控投影 |
| 普通知识解析 | 现有 PDFBox/POI/Tika 路径，补定位及资源关闭 | 不是所有文件都转成纯文本；保留原件与结构 |
| 复杂PDF、扫描件、表格 | Docling 独立解析插件 | 条件启用；模型权重、OCR、依赖单独准入 |
| 知识查找 | 授权目录/全文/结构定位 + LangChain4j RAG + Qdrant | 精确问题直接读文件；跨文档语义问题用混合检索；共用授权 |
| 会话上下文 | LangChain4j ChatMemoryStore 接口与业务消息存储 | 短期上下文窗口不代替业务历史；须补实际持久化及错误处理 |
| 长期记忆 | 有版本、有来源的 Markdown 文档，复用 MemoryVersion/ExperienceProposal | 数据库存放归属、版本指针、状态、来源与授权；不首期引入独立记忆平台 |
| 本体关系 | 现有业务ID + KnowledgeAssertion/来源关联 | 先回答负责人、依据、版本、上下游；图数据库按需求再引入 |
| 经验整理 | 现有任务运行器生成独立候选、差异、评测后发布 | 不原地自动重写共享记忆；不新增第二个 Agent 循环 |

这是本项目的设计推导，组件功能事实和适用限制见下文。选择数据库驱动、对象存储、模型服务和打包方式仍须完成54号整包准入，不因上表选中若干宽松许可组件而自动商用放行。

## 3. QoderWake可以借鉴什么

QoderWake官方将项目定义为可重复使用的工作目录及访问关系；项目配置不会复制原文件，删除配置也不删除磁盘目录。公开与Waker私有项目的范围不能等同于本项目的企业人员授权，多Waker并行修改需要隔离和汇总。[项目说明](https://docs.qoder.cn/qoderwake/projects)

知识库面向稳定、反复使用的主题；原资料与编译知识卡分开，上传完成、编译完成和问答验收是不同状态。成员共享与分配给Waker也是不同关系。官方明确删除知识库不会清除历史聊天或撤销已发回答。[知识库说明](https://docs.qoder.cn/qoderwake/knowledge-base)

记忆用于跨任务的稳定规则和经验，支持不同作用域、Markdown编辑、时间线与整份MEMORY.md版本恢复。角色配置还另有身份、行为文件。应借鉴可编辑、可解释的体验；不复制文件命名体系，也不把角色文字当权限执行器。[记忆说明](https://docs.qoder.cn/qoderwake/memory)、[员工配置](https://docs.qoder.cn/qoderwake/manage-wakers)

**设计推导**：本项目采用同源文档与派生卡片两种视图，卡片记录准确的来源版本，不让维护者同时维护两份同义事实。人工改变卡片业务含义时，另存正式知识条目及其版本和来源，不能继续冒充原文。任务内临时资料不自动进入共享知识；被采用的交付不自动变成通用规则；数字员工能后台使用资料不意味着发起人可读。范围以租户、人员、任务、用途和期限确定，不能只按Waker ID隔离。

## 4. 与其他最新实践交叉验证

Anthropic上下文工程强调轻量引用与按需加载，文件导航和检索可以组合；长任务需要可恢复记录与可验证产物。[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)、[长任务实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

2026版Claude Memory进一步提供按作用域的文本存储、只读/读写资源、内容哈希前置条件及历史版本。删除当前条目不等于删除历史。Dreams将整理结果写入独立新存储供审查。这支持文档式受控记忆，但其托管服务、权限和付费能力不能直接计为本项目已获得的开源能力。[Memory现行文档](https://platform.claude.com/docs/en/managed-agents/memory)、[Dreams现行文档](https://platform.claude.com/docs/en/managed-agents/dreams)

OpenClaw也提供工作空间与记忆文档机制，可作为文件型上下文的另一实现参考；工作目录、运行身份和沙箱必须分别理解。这里仅借鉴公开行为，不引入其整个执行框架。[工作空间](https://docs.openclaw.ai/concepts/agent-workspace)、[记忆](https://docs.openclaw.ai/concepts/memory)

**综合判断**：文档式管理符合当前实践，纯文件夹、纯向量库、自动记忆引擎三者单独使用都不足以承担本项目的企业协作治理。文件让人和Agent容易工作，业务服务负责权威状态与授权，索引帮助查找；三者通过稳定对象ID和内容版本连接。

最新许可修正：Weaviate固定HEAD的根LICENSE明确按目录划分，`wl/LICENSE-WEAVIATE`写明2026-08-26及“保留全部权利”，本轮未见其中提供通用再分发授权。因此不能从旧版BSD结论推定最新整包可自由闭源交付，也不能仅将`WEAVIATE_LICENSE`设为关闭就宣称完成许可隔离。备选需核实际制品；优先Qdrant减少这一未决项。[根许可][w-license]、[BSD子集许可](https://github.com/weaviate/weaviate/blob/77063adc7497182f688a0bcefa099c9232f6e6e8/LICENSE-BSD)、[受限目录许可](https://github.com/weaviate/weaviate/blob/77063adc7497182f688a0bcefa099c9232f6e6e8/wl/LICENSE-WEAVIATE)

### 6.2 为什么不是直接接入RAGFlow

RAGFlow适合需要成熟资料处理、检索配置界面的专门知识服务。本次README给出至少4核、16GB内存，并含MySQL、文件存储、队列与文档索引组件；这是上游启动要求，不能当本项目容量规划。它已包含Agent与Memory，接入时只能限定所需解析/检索接口，不能形成第二个权威执行链。[说明][r-readme]、[Compose][r-compose]

本项目已有OA、员工、文件、知识页面和SDK；重用底座+按需Docling比整体嵌套另一平台有更清楚的边界。若真实材料证明该组合在复杂文档质量上持续不达标，而RAGFlow同组POC明显更好，可替换解析/检索实现。判据见56号，不能仅凭演示界面丰富度决定。

### 6.3 为什么不是用Mem0保存所有聊天

Mem0的提取、增删改和历史能力有价值，但user_id等过滤字段不能代替可信业务身份。专项读取发现部分接口仅校验API凭据，按请求字段选数据；历史保留旧值也意味着删除当前记忆不是全量遗忘。它可产出候选偏好与经验，正式内容仍需来源、确认、作用域和版本。Graphiti最近发行包含group隔离相关修复，进一步说明集成版本和隔离测试不可省略。[独立源码笔记](../../validation/knowledge-memory/memory-candidates-research.md)

### 6.4 文档树和向量检索如何取舍

PageIndex当前本地模式使长文本PDF目录推理值得实测，但其海量文档File System属于Cloud-only。供应商金融基准不能推导为本项目所有文档最优。本项目先采用文档目录/章节定位与混合检索共存：已知文件读章节；语义问题检索；需要跨章节论证时有限追加读取。不能因采用文件形式就断言不再需要索引，也不能把每次文件读取都升级成多轮模型搜索。[PageIndex现行README][pi-readme]、[树搜索](https://docs.pageindex.ai/tutorials/tree-search)

## 8. 成熟度判定与采用门槛

首期组件必须同时满足：有可固定的发布制品；可解释的许可及子依赖；已有接口或有限适配；离线/私有部署符合数据策略；权限和删除可实现；备份恢复路径明确；用项目样本跑通正常和失败流程。以上是采用门槛，不是已经全部通过。

本轮发现并纳入改造的关键问题：查询无业务filter、缓存缺少授权范围、会话更新空实现、全文/重排降级含糊、解析缺少位置、共享记忆并发/范围/删除闭环不足、最新与底座依赖版本不同、整包商业交付未放行。56号给出职责分配、最小接口和逐项POC。

研究完成可以交付具体推荐；**产品正确、业务权限有效、模型效果更好、整体完整商用，仍需运行与最终构建证据。** 原173项需求与72个产品验收场景不因本轮研究改为已完成。
