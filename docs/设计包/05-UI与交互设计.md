# UI 与交互设计

范围：22 个页面/交互组覆盖全部 153 项需求；它们是当前页面的重组与增量设计，不是另建 22 套应用。现有 87 页清单继续作为全平台页面资产；本包不把历史截图覆盖数当作当前视觉验收。当前v2.6原型演示41个职责视角、OA多事务队列与任务隔离，详见第14节；v2.4结果按历史阅读。

## 1. 信息架构与角色入口

现有 13 个逻辑权限槽位继续使用。侧栏“工作”内区分工作台和工作执行；高频资源保持数字员工、知识、技能、工具入口；低频团队、自动化、渠道、方案从相关对象渐进进入。是否显示来自服务端页面能力、对象关系和 allowedActions，不能按“管理员/普通人”二分硬编码。

| 视角 | 首屏重点 | 默认主动作 | 辅助信息 |
|---|---|---|---|
| 主执行人 | 我的目标、交付、协作分工与待合并贡献 | 开始/继续工作或提交交付 | 下一接收人、输入变更、完成检查 |
| 协作人 | 我的专业分工及主任务提供的授权背景 | 配置自己的 Agent、提交专业贡献 | 主任务要求、需要我重核的变更 |
| 审核/审批人 | 待我决定的请求与版本差异 | 接受/退回或批准/拒绝 | 证据、检查结果、职责分离提示 |
| 流程设计者 | 节点合同、岗位解析、分支与缺口 | 编辑、预检、员工预览 | 发布 Diff、在途影响 |
| 资源维护者 | 资源内容、版本、依赖与可用性 | 编辑草稿、测试、提交发布 | 使用反馈、健康、撤销影响 |
| HR/身份/权限管理员 | 各自领域的待处理事项 | 已有精确授权允许的命令 | 影响预览、交接、审计 |
| 运维/审计 | 健康或证据，只读内容按范围裁剪 | 诊断/授权恢复/审计查询 | 原始关联、未知效果、真实用量 |

角色演示切换器只存在于交互原型的演示工具栏，正式产品不能让用户通过切换视角获得权限。

## 3. P02 节点工作区结构

v2.3 依据 QoderWake 实际 UI 调整为桌面侧栏 240px，1050px 以下收至 210px，700px 以下为可展开移动导航；主内容自适应。详情按内容使用弹窗或按需侧栏，表单最大宽约 900px。本HTML原型继续保持独立演示；产品成熟组件体系的候选选型见22号文档，正式接入时统一Token、控件和现有路由，避免多套UI体系。

~~~text
┌ 工作 / 设备采购 / 方案编制                 待我处理 · 截止周五 ┐
│ 目标：形成可审核采购方案       我的职责：主执行与汇总          │
│ 输入：设备清单 v2、预算 v1     交付：方案、设备表、预算表      │
│ 下一接收人：采购审核岗         提醒：预算需依据新清单重核      │
├ 任务与对话 | 协作分工 | 本次配置 | 上下文 | 产物与交付 ──────┤
│                                                            │
│ 当前标签内容；对话与业务任务始终绑定同一工作项                 │
│ 业务事件、资料引用、贡献卡、工具确认采用不同可读组件           │
│                                                            │
├ 完成检查：2/3 项通过               [保存草稿] [提交交付]      ┤
└ 提交不可用时，旁边明确列出待解决条件及可进入的恢复位置         ┘
~~~

顶部始终保留目标、责任、交付和下一步；运行日志放诊断抽屉。不能把所有资源编辑表单平铺在节点首屏。标签切换保留草稿、筛选和滚动；刷新后由服务端重新读当前任务/配置/状态。

## 4. P03 协作面板

参与者卡显示姓名/职责、分工目标、期限、可见 Agent 名称与状态、贡献版本及下一动作。头像或 Agent 名称点击只能进入用户有权读取的摘要；不暴露他人私人记忆、连接账号细节或全部历史。

“请人协助”表单：协作人（授权候选）、具体目标、需要的输入、交付格式、期限、范围、是否影响已有完成条件。新增必需贡献只能来自节点允许的策略。提交后显示待接受；接受后创建合法协作工作，显示“打开我的分工”。主执行人不能代替协作人在自己的配置面板修改对方 Agent。

贡献卡分草稿、待接受、已接受、被退回、待重核、已替代；卡内可预览版本与依据差异。主执行人的“接受贡献”不能与“提交节点”使用同一按钮。

## 5. P04 本次配置表单合同

| 字段 | 控件 | 必填/默认 | 校验与解释 |
|---|---|---|---|
| 执行方式 | 单选 | 节点允许的模式 | 人工保留；自动仅符合现有风险规则时可选 |
| 数字员工 | ObjectPicker，分我创建/共享/推荐 | 非人工必填 | 显示用途、版本、可用原因；服务端 eligible 集合 |
| 技能 | 多选卡 + 参数子表单 | 节点必需项锁定 | 参数按 schema；依赖/冲突/顺序可解释 |
| 知识 | 必需资料 + 可追加来源 | 必需版本不可移除 | 解析/发布/过期/可读状态分开 |
| 连接器与动作 | 应用动作卡 + 身份选择 | 用到外部能力时必填 | “以谁的账号执行”；只展示授权身份摘要 |
| 工作空间 | 授权空间与目录选择 | 有文件操作时必填 | 浏览器不默认读用户本机路径 |
| 执行方案 | 单Agent/已启用团队/技术方案 | 合格默认 | 条件能力未认证不显示可运行 |
| 预算与模型 | 继承摘要 | 租户配置 | 说明不可更改原因；不添加员工级供应商凭据 |
| 输出格式 | 合同字段/允许的选项 | 交付合同默认 | 不放宽必需交付格式 |
| 补充要求 | 多行文本 | 可选 | 明示只作本次补充，不覆盖业务硬约束 |
| 保存范围 | 本节点/个人偏好/模板提案 | 本节点 | 跨节点复用时重新资格校验 |

点击保存并不启动。点击开始前显示服务端解析的有效组合和缺项；合格低风险工作无需为每个配置重复审批。更改运行配置须看影响，并产生新尝试或受支持的更新，不静默改旧快照。

## 6. P20 上下文面板

顶部用业务语言：“当前依据：设备清单第 2 版；预算协作尚未应用更新”。下面分四区：

1. 本次共同事实：目标、硬约束、交付标准、已确认决定和有效版本。
2. 此次使用资料：名称、版本、来源、用途、是否必需、可读/缺失；敏感内容按权利裁剪。
3. 更新影响：改变了什么、影响哪些本人可见任务/贡献、需要谁处理。
4. 处理状态：准备中/已送达/有装载证据/更新待应用/失效/冲突，附对应恢复动作。

“资料已送达”“我已阅读”“数字员工已有装载证据”“结果通过检查”分别显示，不用一个绿色“已同步”覆盖。技术 hash、seq、epoch 只在诊断中显示；普通用户看到版本、原因和责任人。

关键输入缺失时阻止相关执行，按钮给“补齐资料”；可选背景缺失时说明降级范围。用户纠正业务事实需当前修改权，纠正私人偏好不能改变其他人的共同基线。

## 7. P16 交付与审核

交付区按项目列出文件版本、结构化输出、检查项、未决问题、外部回执和接收对象。逐项“通过/未通过/阻塞”对应 CompletionCheckResult 的真实检查，不由模型句子推断。专业审核和高风险动作审批用不同卡，清楚显示需要做的决定和影响。

提交按钮触发时再验当前 revision、资格、贡献基线、必要审批和引用可读性。冲突保留草稿，展示变更并定位“重核”；结果待确认时展示查证状态。成功后展示不可变包与下游接手状态，不能仅 Toast 后清空页面。

## 8. 设计系统与通用交互

v2.3 原型结合 QoderWake UI：白色主区、#F9F9F9 侧栏、#141414 正文与主按钮、#E6E6E6 边框、#EAF7E7 工作记录区；绿色作为品牌和进展强调。4–8px 圆角，紧凑线性图标，不以颜色单独表达状态。正式主题与公司品牌 Token 的映射由产品现有设计系统承载，本轮未修改生产主题或引入 UI 库。

复用 ActionButton、DataState、CommandDialog、ObjectPicker、Timeline、EvidenceLink、WorkThread/Composer、Diff 等组件合同。表单标签常驻；错误与具体字段关联；操作后焦点回到触发点或结果标题；消息流不要抢焦点。

十类页面状态必须设计并验证：加载、授权空态、正常、部分数据、请求失败、无权/不存在、只读、提交中、版本冲突、结果待确认。空态只在明确允许查询且确无数据时出现；403/网络失败不能伪装为空列表。

## 9. 响应式与可访问性

- ≥1280px：完整侧栏，内容加可选辅助区；高密度数据用表。
- 768–1279px：侧栏收起，右栏改抽屉；固定主操作不盖住正文。
- <768px：单列、任务摘要压缩，配置逐段展示，表格改字段卡；SOP/技术画布提供节点列表与表单。
- 检查中文长名称、英文长链接、200% 缩放、键盘、读屏、焦点可见、暗色与 reduced-motion；原型的有限检查不等于这些项目全部通过。
- 破坏性操作和高风险动作沿现有风险分级；与普通保存使用不同确认组件。对已授权可逆动作不额外堆叠确认。

## 10. 原型范围与开发交接

v2.4交互原型使用虚构业务与管理数据，提供41个职责视角，覆盖当前合同全部44个人类角色键。业务视角演示各自配置、上下文变更、贡献重核、审核、交付与接手；资源、组织、权限、审计和运维视角分别呈现对应领域操作。服务身份不进入员工导航。它不连接业务服务，也不伪造 DSH 装载或外部系统调用。

原型是交互说明，不是全平台实现。未在原型演示的页面仍有本文件 P01–P22 字段/动作/状态合同和 153 条故事验收。开发按当前路由、组件和消费者接入，不能复制原型脚本成为生产权限或业务状态源。


## 11. 员工市场的可见入口与交互

P22为员工与资源维护者共享的跨资源入口。工作区可发现“资源市场”，本次配置有“从市场添加”；不要求员工进入后台。市场按数字员工、技能、工具筛选，提供授权详情、复制并使用、我的复制和来源版本。个人副本成功后回本人节点选中对应资源。

市场浏览、复制、编辑、使用与管理动作分别授权；不同用户的可见集合和计数均经服务端投影。可看不可复制者仍可读授权详情；缺依赖/连接/发布的副本显示具体恢复条件。低风险已授权直接采用不追加重复审批。原型按显式演示授权夹具验证差异，不是生产权限实现。详细字段、空错态、作用域与十项验收见 [员工市场复制与使用设计](<12-员工市场复制与使用设计.md>)。

## v2.6 产品主旨、B/S与字段核查

本项目是以 OA 工作流为基础的企业 B/S 协作软件：流程连接人、责任和任务，由承担人在自己的任务内配置数字员工。业务发起 → 人员待办 → 本人配置数字员工 → 执行与确认 → 审批或交接 → 下一位承担人。既有平台能力全部保留。
