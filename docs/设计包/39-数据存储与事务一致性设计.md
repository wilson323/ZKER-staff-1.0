# 数据存储与事务一致性设计

技术设计1.0｜2026-09-11｜`PROPOSED_DATA_MODEL / NO_MIGRATION_EXECUTED`。逻辑字段和状态以[27号](27-逻辑数据模型与接口契约.md)为准。本文件将其映射为拟议物理结构、约束、事务和恢复方式；不是已验证的建表脚本。

## 1. 数据组件与命名

芋道条件性实现映射使用**MySQL优先兼容验证路径 + 其已集成Qdrant向量实现 + 原缓存接口**，固定兼容版本后才能实施。PostgreSQL单库+pgvector是该路线的后续简化实验：本次36号核验发现芋道MySQL/PG公开初始化均缺BPM/AI应用表，须补齐合法DDL；其AI工厂也没有开箱pgvector，不能靠减少服务数就宣称总工作更少。RuoYi-AI的SQL覆盖与向量适配需按其自身固定代码验证，不能套用芋道结论。普通Redis缓存不能假设具备向量查询能力。

拟议扩展表统一`oa_`前缀，实际命名在M0根据底座表清单去重。ID外部用opaque字符串，数据库使用底座一致的ID类型；引擎ID保留字符串引用。每个关系含tenant_id，唯一键、索引和join必须限定tenant。历史引擎表不加未经验证的外键/索引；只通过适配器维护关系，并以真实回读/对账证明存在性。

时间UTC微秒精度，业务日期独立DATE，金额DECIMAL并带币种。JSON只保存不可变配置/证据快照和有版本Schema的扩展，不能代替所有可筛选的状态、主体和关联列。大型产物存私有对象存储，数据库存版本、digest、大小、分类与storage_ref。

## 2. 物理对象映射

| 逻辑对象 | 拟议物理归属 | 核心约束和索引 |
|---|---|---|
| Person/Org/Membership | 既有system表 | 不复制账号；可信租户/任职查询；离岗撤销关联授权 |
| ProcessDefinition/Instance/HumanTask | 既有bpm服务与Flowable表 | 通过合法API读取/办理；流程版本固定 |
| WorkItem | oa_work_item | UNIQUE(tenant,engine_task_ref,activation_epoch)；任务状态不成为第二引擎状态；索引(tenant,assignee,status,due_at,id) |
| TaskAgentBinding / BindingVersion | oa_binding_head + oa_binding_version | head按tenant/work唯一；版本不可变；head指针只条件更新；角色/模型/技能/工具/连接版本引用固定 |
| ExecutionSnapshot / ContextManifest | oa_execution_snapshot + oa_context_manifest | work、binding、epoch、policy、sourceRefs、digest固定；人员与后台manifest用途区分 |
| ContextApplication | oa_context_application | UNIQUE(manifest,consumer,attempt)；observed/applied序号不倒退；有证据才能loaded/applied |
| ExecutionAttempt | oa_execution_attempt | work、snapshot、state、fence、lease_until、checkpoint、budget；UNIQUE(tenant,work,intent_key) |
| ToolInvocation / ToolEffect | oa_tool_effect | UNIQUE(tenant,attempt,logical_action_id)；请求digest、外部业务键、receipt、UNKNOWN/CONFIRMED状态 |
| CollaborationRequest/Link | oa_collaboration_request / oa_collaboration_link | 子工作最多一个协作父关系；非自指；接受时事务内防循环；UNIQUE(tenant,request_id) |
| Contribution/Version | oa_contribution | UNIQUE(tenant,link_id,version)；提交后不可变；决定引用当前父/子基线 |
| BusinessFact/Baseline | 源业务表 + oa_fact_baseline | 权威值回源；baseline保存不可变已确认版本集合；索引(tenant,work,version) |

| CompletionCheck | oa_completion_check | workRevision+epoch+baseline/artifact/contribution/policy摘要固定，变更则失效 |
| ReviewRequest/Decision | 底座审核任务 + oa_review_target | 审核targetDigest唯一定位；独立审核资格由服务端判断，不能从普通聊天写批准 |
| DeliveryCommit/HandoffPackage | oa_delivery_commit / oa_handoff_package | UNIQUE(tenant,work,epoch)；版本不可变；交接包引用和接收范围固定 |
| HandoffReceipt | oa_handoff_receipt | UNIQUE(tenant,package,recipient_work,epoch)；接手前必需引用当前可读 |
| PublishedAsset/Version/Lineage | 复用AI/技能资产 + oa_asset_version / oa_adoption | 发布版不可变；UNIQUE(tenant,actor,type,source_version,intent)；COPY与REFERENCE分列 |

| ExecutionGrant/OutputRelease | oa_execution_grant / oa_output_release | subject、work、purpose、actions、resource版本、expires、policyVersion、revokedAt；发布绑定具体产物digest与接收范围 |
| KnowledgeAssertion/EntityLink | oa_knowledge_assertion / oa_entity_link | 候选、确认、发布分开；source/version/fragment；对象ID回原业务；不复制主数据 |
| MemoryEntry/Feedback | 复用既有记忆结构或oa_memory_entry / oa_feedback | owner/purpose/sourceRun/version/retention；反馈含义有限；共享有独立范围 |
| ConfigProposal | oa_config_proposal | base_revision+字段级before/after+scope；采用回原命令；不能重复复制配置权威 |

所有私有数据关联通过复合外键或同事务等价守卫验证tenant一致；FK不等于授权。软删除不能复用历史幂等键或令旧链接指向新对象；对唯一约束要求显式测试软删除策略。长列表keyset分页，排序键包含稳定id，不靠offset读取持续变化的大型待办。

## 3. 核心事务与幂等

| 命令 | 原子边界 | 失败后可观察状态 |
|---|---|---|
| C02 发起 | 幂等operation、表单版本、底座startProcess、首任务映射、Outbox | 同库失败全部回滚；跨事务不得显示已发起，按业务键查证 |
| C03 领取/转办 | 引擎合法任务操作、WorkItem责任代次、新绑定失效、撤权事件 | 旧运行fence/epoch禁止写；新承担人另确认 |
| C06 开始 | 锁当前work/head、重验输入/动作、预留预算、快照、Attempt、Outbox | 队列未派发也有唯一attempt；重试返回同operation |
| C09 接受贡献 | 当前父/子版本、贡献决定、父工作revision和事件 | 通知失败不回滚已接受贡献，重新派送通知 |
| C11 提交 | 完成检查、批准digest、不可变交付包、底座任务办理与Outbox | 目标原子事务不成立时PENDING_COMMIT，查证后才COMMITTED |
| C12 接手 | 接收责任与必需附件读权、接手回执、原任务处理 | 通知已读不算接手；不可读返回恢复事项 |
| C13 采用 | 幂等operation、资源定义副本/引用与谱系 | 依赖部分失败可继续同操作；不给副本注入作者凭据 |

同键同请求返回原结果，同键不同请求返回409。作用域至少tenant+actor+command+idempotencyKey，不能按HTTP连接重试次数生成新意图。数据库唯一冲突必须重新加载原operation并比较digest；不是捕获异常后盲目重试。

C11锁顺序固定为work→binding head→attempt→completion target→delivery，再通过同一事务管理器调用底座服务。适配引擎若锁顺序不同，以真实并发测试和统一重试政策修订；死锁只回滚尚未发生外部效果的本地事务。不能持锁调用LLM/外部工具。查读用主库验证正式动作，展示可用有水位的只读投影。

## 4. Worker租约与恢复

队列领取使用短事务条件更新或`SELECT ... FOR UPDATE SKIP LOCKED`，提交后才执行任务。SKIP LOCKED只用于队列竞争，不用于“完整业务列表”的一致查询；这是[MySQL锁定读取文档](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)指出的适用边界。

```text
1. 领取READY且可到期重取的派发项 → fence递增，写lease_owner/lease_until。
2. Worker按租约续期，执行开始前与每次工具动作前查询当前grant/epoch。
3. 每个业务动作使用稳定logical_action_id；先登记意图，再调用外部系统。
4. 结果回写同时比较attempt、fence、responsibilityEpoch与授权版本。
5. 租约到期只允许新Worker取得更高fence；旧Worker回写被拒绝。
6. 恢复时先查ToolEffect。UNKNOWN须查原效果；不得仅因Worker崩溃重发写操作。
```

只读/纯计算步骤可从最近可信检查点重做；工具写入步骤要有目标幂等能力或可查业务键。不支持这两者的目标出现未知效果时，转人工核对并冻结后续依赖。预算释放只释放未消耗预留，模型超时仍可能被计费，保留待对账记录。

## 5. 交付和来源变更

ArtifactVersion、Contribution和DeliveryCommit分别不可变。输入更新形成新baseline并使相关候选/检查/审核失效；不原地改旧交接包。计算来源依赖索引，按work生成需重核事件，禁止把一个人的局部聊天变更扩散为全组织事实。已交付后变更通过补充/返工工作关联旧包。

文件上传两阶段：申请上传引用→私有暂存→确认digest/大小/mime→扫描/解析→可用版本。上传200不代表解析成功。引用先入PENDING，只有存在且合格的对象才可用于正式交付；失败可删除未引用临时对象，但真实删除由保留政策和授权办理。

向量是派生索引，可从获准源重建；源撤权立即影响检索与读取，不等待索引异步删除完成。模型/维度变更新建collection/index版本并双读验证后切换，不能把不同向量空间混入同一检索。分析读库使用独立只读身份、列/行约束与确定性口径，不能给模型通用生产SQL账号。

## 6. 迁移、备份与删除

DDL采用底座一致的版本迁移方式，扩展变更先expand、回填、双兼容读取、再contract。每次迁移记录schema版本、输入提交、行数/约束核对和失败恢复；建表SQL必须经过干净库与旧版升级两条验证。执行本技术设计没有运行数据库迁移。

备份必须覆盖同一恢复点的业务库、文件版本和连接配置引用；秘密本身按组织密钥备份制度管理。恢复后禁止自动补跑旧外部写入，先核operation、任务责任、授权有效期和工具回执。保留/删除请求与审计冻结冲突时形成有权处理事项；不得用删除向量替代删除源数据，也不能用软删除宣称全部物理副本已消失。
