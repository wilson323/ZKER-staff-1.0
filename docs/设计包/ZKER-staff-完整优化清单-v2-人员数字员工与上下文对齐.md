## 0. 本次补全：执行人、协作人与数字员工如何共同工作

本版按“协作人”理解用户消息中的“写作人”。如果指实际负责撰写材料的人，则他属于承担“内容编写”职责的执行人或协作人，下面的关系仍适用。

**执行人和协作人共同完成一项业务工作；各自选用的数字员工承担被明确分配的执行任务。数字员工的归属、使用授权、当前任务分工和业务责任必须分别记录。**

上一版在 HR、NC、TM、MM 和 RS 中覆盖了这些主题，但对“同节点多个人分别带自己的数字员工协作”及其上下文一致性写得不够具体。本版保留原 123 个编号，补充 HC/CX/SY 三个领域的 30 条验收要求，共 153 项；新增条目细化既有主题，实施时应合并到关联任务包，不能机械新增 30 套对象或接口。

### 0.1 关系模型：人负责工作，数字员工承担具体执行

| 对象 | 与人的关系 | 对当前工作的职责 | 不应混淆的事情 |
|---|---|---|---|
| 节点责任人 | 对该节点业务结果负责的人 | 确认责任、协调异常、按合同确认交付 | 可以与执行人相同，也可以不同 |
| 主执行人 | 当前节点实际承担主要执行工作的人员 | 接受任务、拆分协作、汇总结果、发起提交 | 是任务中的角色，不意味着行政上领导其他协作人 |
| 协作人 | 承担被分配的具体协作职责 | 确认协作范围、完成分工、提交贡献、处理返工 | 有协作权限不等于能改主任务要求、改别人 Agent 或代替审批 |
| 主执行人的数字员工 | 由主执行人在授权范围内选用 | 执行主工作或汇总、检查、整理等任务 | 不能以“我是主 Agent”替代人类责任或扩大权限 |
| 协作人的数字员工 | 由协作人在授权范围内选用 | 在协作范围内完成专业工作，形成贡献结果 | 其归属不会因为参加协作转移给主执行人 |
| 共享数字员工 | 多个人获得使用权的同一 AgentProfile/版本 | 为不同人创建隔离的任务执行 | 共享角色配置不等于共享私人记忆、连接身份和全部会话 |
| 审核/审批人 | 由节点合同和授权确定的独立职责 | 审核成果或批准具体受控动作 | Agent、专家意见、已读消息不能替代正式决定 |

主执行人和协作人都可以有零个、一个或多个数字员工；也都可以使用共享数字员工。选择来自当前节点/协作任务的合格集合，不要求平台把“一人一 Agent”写死。一个数字员工也可参与多个任务，但每次运行必须隔离工作范围、配置和上下文。

依据：[人机协作主链](</Users/mac/Documents/ChatGPT/ZKER- staff/docs/product/human-digital-employee-collaboration-chain.yaml:10>)、[角色合同](</Users/mac/Documents/ChatGPT/ZKER- staff/docs/security/business-role-ui-projection-matrix.md:16>)、[Agent 与工作项领域模型](</Users/mac/Documents/ChatGPT/ZKER- staff/CONTEXT.md:94>)。

### 0.2 三种协作方式需要明确区分

| 方式 | 如何组织 | 上下文如何对齐 | 成果由谁确认 |
|---|---|---|---|
| 同一节点，多个人各带自己的 Agent | 主执行人负责主任务，协作人各自领取清楚的协作工作；使用独立执行范围 | 同一业务基线与共享决定，加每个人/Agent 的授权资料投影 | 协作人确认其贡献；主执行人汇总；节点责任/审核按合同完成 |
| 同一人员使用多个 Agent/团队 | 属于该人员执行任务的内部技术分工 | 共享任务目标，成员获得各自子任务与所需资料，汇总有来源 | 仍由原人员承担业务责任，不产生多个自然人责任主体 |
| SOP 不同节点之间的人机交接 | 上一个节点提交，下一节点激活并分配给下一人 | 不可变交接包 + 下一接收人/Agent 的重新授权上下文 | 下游按接收标准确认，必要时退回原责任范围 |

“让 Agent 互相发消息”只覆盖技术通信。跨人协作还需要记录谁邀请了谁、为什么协作、具体交付是什么、谁可以改变要求，以及贡献如何被接受。

**与当前代码的一致性约束：** 当前数据库迁移定义一个 WorkItem 只能有一个 active AgentAssignment；创建分配时也更新 work_items.current_assignment_id。不能让每位协作人把自己的 Agent 都写到同一主 WorkItem 的当前分配，覆盖前一个人的执行。建议将有独立 AI 执行需求的协作分工映射到独立、合法关联的工作单元，各有 Assignment/Attempt，最后向主工作提交贡献。人类协作责任优先复用已有 HumanTask/有界 Delegation；需要的父子关联、汇总规则与 PROCESS/AD_HOC 映射先补合同，本文不声称这些父子字段已存在。[唯一有效分配约束](</Users/mac/Documents/ChatGPT/ZKER- staff/services/control-plane/alembic/versions/20260903_0045_pk05_agent_candidate_domain.py:457>)、[分配写入](</Users/mac/Documents/ChatGPT/ZKER- staff/services/control-plane/control_plane/agent_assignment_create_session.py:107>)。

### 0.3 四种关系分别管理

| 关系 | 需要记录 | 变化的影响 |
|---|---|---|
| 资产归属 | Agent/技能/知识由谁维护，当前发布版本 | 更换维护者走资产交接，不随任务邀请自动改变 |
| 使用授权 | 哪个人可对哪项资源做什么、何时失效 | 可使用不自动可编辑；分享上下文不自动获得执行权 |
| 本次任务分工 | 主任务、协作工作、承担人、所用 Agent、范围与期限 | 重新分工要更新责任和执行资格，旧执行须受约束 |
| 业务结果责任 | 谁确认专业贡献、谁汇总、谁批准、谁最终提交 | Agent 运行完毕不会自动改变人的完成责任 |

主执行人可以向协作人提出任务请求；是否自动接受取决于预先授权的分派规则。请求协作不等于获得对方数字员工的管理权限。跨 Agent 调用必须有允许的协作通道和明确作用域；在已有授权范围内可以自动执行，无须每条消息都重新审批。只抄送信息时提供只读投影；要求对方代办动作时另外校验具体委托，不以抄送代替授权。依据 [工作交接、抄送与数字员工上下文](</Users/mac/Documents/ChatGPT/ZKER- staff/docs/identity/organization-identity-access-design.md:352>)。

### 0.4 上下文分层：对齐业务事实，不复制私人工作空间

“共同业务基线”是现有 WorkItem、版本化业务对象和已确认决定的组合视图，不能另建平行事实库。“有效上下文包”也是现有 ContextManifest、执行快照及其引用的组合，不是另一套运行时。

| 层 | 包含内容 | 共享方式 |
|---|---|---|
| 流程层 | 业务目标、SOP 版本、节点关系、节点必需完成条件 | 参与者读取其授权范围内的流程投影 |
| 节点/主任务层 | 当前目标、输入版本、约束、分工、已确认决定、未决问题 | 必要共同事实使用同一权威版本 |
| 协作工作层 | 此协作人的子目标、允许动作、交付格式、期限与依赖 | 交给承担该分工的人和所选 Agent，不混入无关子任务 |
| 数字员工能力层 | 职责配置、技能版本、工具、知识与允许的运行策略 | 由已发布版本与本次有效配置冻结，不能覆盖业务硬要求 |
| 个人层 | 私人偏好、私人记忆、私有草稿、个人连接身份 | 默认保留在本人授权范围，显式发布的业务贡献才进入共享记录 |
| 运行层 | 当前输入、必要历史、工具回执、产物引用和执行状态 | 每个 Attempt 独立；公开结果可发布，内部推理不作为交接资料要求 |

业务完整性和保密性需要同时满足：接收人无权读取但又必须知道的输入，应提示“缺少执行所需资料”，转为授权申请、脱敏替代或重新分工；不能一边删掉关键条件、一边显示“上下文完整”。

现有 ContextManifest 的含义就是面向特定自然人、Agent 或 Role 的目的限定投影；WorkThread 是协作记录；HandoffPackage 是完成后的交接包。三者不能互相替代。[领域定义](</Users/mac/Documents/ChatGPT/ZKER- staff/CONTEXT.md:167>)、[ContextManifest 定义](</Users/mac/Documents/ChatGPT/ZKER- staff/CONTEXT.md:366>)。

### 0.5 上下文对齐需要完整的八步机制

| 阶段 | 系统应做什么 | 用户应看到什么 | 应保留的证据 |
|---|---|---|---|
| ① 建立基线 | 固定主任务目标、必需约束、资料版本、分工、完成标准及未决项 | “当前任务要求”卡片 | 业务对象/输入/决定的来源与版本 |
| ② 按接收者投影 | 根据人、Agent、用途、字段权限、数据等级和有效期选择内容 | “我已获得什么、还缺什么” | 授权决定、源引用摘要、投影摘要 |
| ③ 派发前冻结 | 绑定分工、Agent/能力版本、当前上下文与执行尝试 | “本次执行使用的版本” | Assignment/Attempt 与有效上下文引用 |
| ④ 证明实际装载 | 通过既定 DSH 扩展或 Adapter 边界装载必需上下文 | 已装载/缺资料/待刷新 | Runtime 装载事实，不能只保留磁盘写入回执 |
| ⑤ 检查理解与计划 | 对关键任务生成可审阅的目标、约束和交付检查表 | 工作计划或任务理解摘要 | 公开计划、关键条件映射与必要的人类纠正 |
| ⑥ 变更与补齐 | 有序发布新决定/输入/产物，处理断线与序列缺口 | 发生了什么变化、影响哪些工作 | 事件序列、已接收/已应用版本、失效标记 |
| ⑦ 提交前重核 | 校验贡献依据仍有效，必要条件未遗漏，权限未过期 | 可接受/需更新/冲突待处理 | 基线版本、来源、检查结果与当前授权 |
| ⑧ 交接与再授权 | 汇总被接受结果，生成不可变交接包，下游重新解析 | 下个人收到可执行的任务与必要资料 | HandoffPackage、ContextManifest、接收结果与下一节点关联 |

证据分为四个强度：**已保存、已送达/装载、关键约束理解检查通过、业务结果通过验收**。前一级不能代替后一级。哈希一致能验证内容身份，不能证明模型理解正确；模型自述“已理解”也不能单独证明正确。因此，系统应保证版本、授权、必需资料和提交一致性，并通过可判定规则、专业复核及真实交付物检查语义正确性。

### 0.6 必需字段与现有合同的关系

以下是需要在现有对象及其组合投影中可追溯的信息清单，**不是声称这些字段都已存在于一个 Schema 中**。应复用已有字段；缺失部分在既有合同中明确引用关系，禁止前端临时拼成权威事实。

| 信息组 | 应能追踪的内容 | 当前证据及待补充点 |
|---|---|---|
| 工作身份与分工 | 业务实例、主 WorkItem、协作工作、承担人、所用 Agent、Assignment/Attempt | 已有 WorkItem/Assignment；多人独立协作的合法父子关系和贡献汇总需补齐 |
| 业务基线 | 目标、约束、交付标准、已确认决定及各自版本 | 文档已有；不能只从最新几条对话推断完整要求 |
| 源与有效投影 | sourceWorkItemId、用途、接收者、源引用与投影摘要 | ContextManifest Schema 已有对应字段，但只含摘要不等于已有完整内容解析器 |
| 执行资源版本 | AgentDefinitionVersion、能力、PluginProfile/配置摘要 | 领域设计要求固定；当前 ContextManifest Schema 无这些直接字段，需与已有执行快照形成可校验关联 |
| 新鲜度 | WorkItem/输入版本、thread 序列、已确认决定水位、装载上下文版本 | WorkThread Schema 有 sequence/revision；跨消费者的“已应用水位”完整协议未证实 |
| 授权与生命周期 | authzEpoch、policyRevision、expiresAt、撤权/删除状态 | Schema 和重授权 decide 已有；授权事实必须来自当前服务端状态 |
| 必需项完整性 | 必需源清单、是否缺失/过期/被裁剪、覆盖哪些完成条件 | 需要从节点合同提取，不能仅检查数组非空或文件存在 |
| 贡献出处 | 作者/运行 Agent、所属分工、依据版本、产物版本、复核决定 | WorkThreadEntry 已有 actor、分类、purpose、digest、contentRef；贡献与具体基线关联需贯通 |

当前 [ContextManifest Schema](</Users/mac/Documents/ChatGPT/ZKER- staff/contracts/jsonschema/context-manifest.schema.json:1>) 使用 additionalProperties=false，不能直接塞入未声明的新字段。需要明确这些信息由哪个既有对象承载，并让消费者验证引用关系。

### 0.7 变更、冲突和信息遗漏如何处理

| 情况 | 应采用的处理 | 不应出现的结果 |
|---|---|---|
| 一般讨论、可选说明增加 | 记录并通知相关人，下一轮按需纳入 | 每条聊天都让所有 Agent 停工 |
| 必需输入/正式决定改变 | 产生新版本，按依赖标记受影响贡献；执行在安全点重核 | Agent 继续用旧合同产出却显示“已对齐” |
| 权限撤销、资料删除、访问到期 | 下一次使用即重授权；阻止受影响动作，清理相关可用投影 | 因冻结快照而永久保留已失效访问权 |
| 当前运行尚未支持补充/恢复 | 保留已有产物，停止或结束旧尝试，创建明确的新尝试 | UI 假装已把新上下文注入运行中的 Agent |
| 两人修改同一结构化字段 | 用预期版本检测冲突，由有权维护该事实的人决定 | 默默以最后提交覆盖有效决定 |
| 多个 Agent 同改文件 | 隔离分支/工作目录或明确串行编辑，合并时比较版本 | 互相覆盖产物但都报告完成 |
| 长任务超出上下文预算 | 保留关键约束和决定；历史按带出处的摘要与按需读取处理 | 简单截断让早期禁止事项、日期或客户要求消失 |
| 消息乱序、重复、离线 | 按序列补齐、去重；同步的是明确业务变更 | 收到消息就视为 Agent 已装载并理解 |
| 摘要与原文矛盾 | 标记冲突，回到授权原文核验，修正摘要并通知依赖工作 | 自动摘要成为不可质疑的事实源 |
| 贡献基于旧版本 | 拒绝过期提交或要求重新检查受影响部分 | 全部无差别重跑，或完全不检查就合入 |
| 下游权限不足 | 显示缺项，完成精确授权/脱敏替代/重新分工 | 先推进下一节点，直到执行中才发现无法读取 |
| 已产生外部副作用后要求改变 | 对照真实外部回执决定补偿或新动作 | 通过改对话状态宣称外部操作已撤销 |

权威次序应由既有合同决定：当前有效业务记录和已确认决定优先于未采纳草稿、讨论、记忆和模型推断；冲突需要显式解决。私人偏好可以影响表达和方法，不能改写节点硬要求。外部文档和工具输出应作为资料处理，不因其中有指令文字就获得修改工作流或授权的资格。

| 管理员 | 角色/资源/授权和连接健康；按管理职责查看元数据，不能默认读取个人原文 |
| 运维 | 派发版本、接收/装载回执、事件缺口、失效与恢复记录；正文按权限最小化 |

“上下文状态”至少区别：待准备、资料不足、待装载、已装载当前版本、发现更新、过期/撤权、冲突待处理。这里是产品展示状态建议，实际状态机须映射既有合同，不另建一套事实源。“对方已看过”与“对方 Agent 已应用新版”必须分开。

### 0.9 具体业务例子与可核验目标

以下是设计示例，未声称真实执行：

A 是方案主执行人，选用方案 Agent；B 是技术协作人，选用技术 Agent；C 是预算协作人，选用测算 Agent。三方共同约束是“客户需求 v3、交付日期 D、批准的方案边界”。B 只看到技术必要资料；C 看到预算授权资料；各自私人记忆和连接账号不互通。

B 提交设备清单 v1，C 据此计算预算 v1。后来设备清单改为 v2，系统应标记预算 v1 的依赖过期、提醒 C 复算，并阻止 A 将旧预算作为最新交付提交。系统可以保留不受影响的方案段落；无需让三个人重做全部工作。A 接受新版预算后，责任人按完成条件提交；下一节点收到被接受的方案、清单、预算、依据和未决事项，并重新授权读取。

如果用户说的“写作人”是文档作者，A 可以负责整合撰写，B/C 提供技术和预算贡献；也可以由 B 负责撰写其中一节。职责由任务分工决定，Agent 不自动继承文档作者的签署责任。

## 1. 按用户最新说明明确产品定位

**本项目用业务流程串联人、职责、任务和交接；每个人在自己的节点里，都应拥有完整的数字员工执行工作台。**

QoderWake 的单 Waker、Group、Skills、连接器、知识、项目、记忆、自动化和技术工作流，都是节点执行能力的重要参照。因此，企业流程与个人执行能力必须同时完善。仅完成分派与审批，会让员工继续回到外部工具处理实际工作；仅增加聊天和资源目录，又不能保证部门间工作真正交接。

更准确的差异是产品组织中心不同：本项目以企业业务实例和人员责任为主线，QoderWake 的公开功能和本机界面以 Waker/Group、任务和资源为主线。**QoderWake 也有人工确认、真人专家、群聊接入和路由，不能把“有人参与”本身当成本项目独有优势。** 本项目需要交付的优势，是持续、结构化地关联岗位职责、节点状态、个人配置、产物、复核和后续交接。[QoderWake 对话与 Group](https://docs.qoder.cn/qoderwake/conversation-tasks)、[@Waker](https://docs.qoder.cn/qoderwake/im-configuration)

## 3. 用户端、设计端与管理端应如何不同

同一个人可以兼任多种职责，界面按当前角色、资源关系和具体动作呈现。以下是工作区组织建议，不是新建一套角色或平行权限体系；继续使用已有角色合同和服务端权限判断。

| 视角 | 首屏最重要的信息 | 日常主要功能 | 配置边界 |
|---|---|---|---|
| 普通员工/节点执行人 | 我现在要做什么、何时交付、等待谁 | 我的任务、节点工作区、我的数字员工、可用资源、工作历史、通知 | 选择有资格的 Agent 和资源；调整本次输入、输出偏好与允许的执行选项 |
| 节点责任人/业务负责人 | 哪个节点堵住、谁负责、影响什么 | 分派/改派、负载、超时、复核、返工、交接 | 在责任范围内处理人员与业务条件；不直接替员工修改个人 Agent |
| SOP 设计者/流程管理员 | 流程结构和每步交付是否清楚 | 画布、责任策略、输入输出、能力要求、配置边界、发布与版本影响 | 决定节点“必须满足什么”和“员工可以选什么” |
| 数字员工/技能/知识资产维护者 | 资产可用性、依赖、待发布变更 | 草稿、编辑、导入、测试、发布申请、版本、共享与使用反馈 | 管理自己负责的资产；无权直接批准自己的受控发布 |
| 组织/身份/权限管理员 | 人员状态、任职、授权和变更影响 | 按各自管理域维护组织、身份、会话、角色、资源授权、离职交接 | 管理域彼此区分；Tenant Owner 不自动等于全域管理员 |
| 审批人/审计员 | 待我决定的具体事项或可复核证据 | 审核范围、影响、依据、批准/拒绝、证据查看 | 分配到的审批可以属于普通业务人员；审计默认裁剪业务内容 |
| 平台运维/模型管理员 | 服务、模型、运行环境、任务积压和成本异常 | Runtime、模型、连接器运行端、容量、升级、备份、诊断 | 维护技术运行；运维身份不自动获得私人聊天和业务审批权 |

依据 E03、E04。目前代码主要采用 member/admin 导航分类，不能代表上述完整投影已落实（E15、E16）。

员工主工作区建议归为“我的工作、对话、数字员工、可用资源、历史”；通知与个人设置放在顶栏/账号入口。技能、知识、工具原有逻辑权限槽位保留，可以通过资源入口和上下文选择器联动呈现。管理中心只对具有对应能力的人出现；高级能力按任务需要展开，而非从产品范围删除。

### 3.1 节点工作区建议布局

| 区域 | 默认展示 | 展开后展示 |
|---|---|---|
| 顶部业务信息 | 任务名、流程位置、本人职责、期限、当前状态 | 上下游责任与必要历史 |
| 左侧任务资料 | 目标、上游输入、必交成果、检查项 | 字段来源、授权的业务附件 |

## 4. 员工可以配置什么，以及怎样生效

**选择范围可以完整，权限范围必须明确。** 员工无需为每次使用已批准的能力重新找管理员；只有超出已有授权或节点要求的操作才走相应申请。

| 配置项 | 员工在节点内的动作 | 流程设计者的约束 | 资产/平台管理职责 |
|---|---|---|---|
| 执行方式 | 人工、数字员工协助、允许的自动执行 | 节点可用模式、是否必须复核 | 提供可用运行能力 |
| 数字员工/团队 | 选自有或共享的合格对象，查看理由与状态 | 岗位能力、数据、风险与候选边界 | 维护发布版本、共享关系、健康与容量 |
| 技能 | 勾选可用技能、填业务参数 | 必需技能/能力和版本兼容要求 | 来源、测试、发布、撤回 |
| 连接器及外部账号 | 选允许的连接器和自己的/被委托的连接身份 | 所需外部动作、目标范围 | 批准连接器、维护服务连接、凭据与健康 |
| 知识与记忆 | 选授权知识版本；选择允许的记忆范围 | 必须引用的资料、禁止跨域的上下文 | ACL、资料加工、保留和版本 |
| 项目/文件 | 选授权项目、附件和工作目录 | 输入输出位置与隔离要求 | 工作空间、存储、设备和网络 |
| 执行方案 | 选单 Agent、团队或允许的技术流程 | 可用方案、输入输出与完成标准 | 发布/维护方案及运行兼容性 |
| 执行预算和偏好 | 在范围内设置期限、输出格式、沟通偏好 | 节点上限及业务要求 | 租户预算、模型绑定和全局策略 |

**模型选择需单独保持设计一致性：** QoderWake 有聊天/任务模型选择；本项目现有角色设计把模型配置放在 Tenant/Runtime 管理侧，禁止员工级模型绑定（E03）。当前优化可以展示继承模型和允许的运行策略；如后续明确要求“每节点任意选模型”，需先修订该产品决策和合同，不能在 UI 中暗中实现。这不是减少执行能力，而是明确谁能配置这一能力。

建议把配置区分为：组织允许范围 → 数字员工的已发布默认配置 → SOP 节点要求 → 人员本次选择 → 执行时冻结的有效配置。权限取交集；参数在允许字段内合并，强制项不可被个人偏好覆盖。

提供三个明确保存动作：**仅用于本次节点、保存为我的偏好、提出共享模板变更**。后两者不能改变已运行的历史版本；更换 Agent 或增加数据权限时显示影响并创建新的执行配置。下一节点继承明确交接的业务资料，不自动获得上一个人的私人记忆、账号连接或全部聊天。

## 6. 完整优化清单的使用方式

- **P0：** 首条真实“人—节点—数字员工—交接”链路及角色正确性的必要条件。
- **P1：** 员工完整执行工作台和管理闭环，必须纳入产品范围。
- **P2：** 扩展复用、复杂协作与规模运营；顺序靠后，不代表删除。
- **修复：** 已定位的不一致或缺陷；**接通：** 已有模块需整合并证明端到端；**完善：** 现有局部能力不足；**补建/核验：** 目标明确，但初版核验时未证明完整实现。

每个域下的“现状”给出代码/设计依据；每条均给出具体优化动作和可观察验收条件。验收条件是后续研发完成标准，本次没有把它们标成通过。

### 7.1 不要遗漏的五条跨模块依赖

1. **节点选择器依赖真实资格查询。** 目录中看得到某个 Agent，不等于它能在当前节点访问当前数据。
2. **资源保存依赖可回读关系和执行时装配。** 只增加一个配置表单不能证明技能/连接器实际参与工作。
3. **私人 Agent 与共享 Agent 都依赖上下文隔离。** 共用 Agent 身份不能共用所有用户的记忆、凭据和工作目录。
4. **自动化与 IM 依赖责任主体和幂等机制。** 定时器触发成功不能替代“这件事由谁负责”的记录。
5. **业务指标依赖结果与交接真实闭环。** 在完成语义不统一前，不能用成功运行数计算自动化收益。

### 7.2 一个目标业务场景

以下为验收设计示例，不是已运行结果：

销售人员收到“整理客户需求”节点，使用自己的需求整理 Agent，选用“访谈归纳”技能与被授权的 CRM 连接，产出需求表。方案工程师接到下一节点，看到需求表、约束和未决问题，选择自己的方案 Agent 或技术团队，绑定产品知识库与方案模板；他不继承销售的个人记忆和 CRM 账号。业务负责人收到方案复核任务，可退回具体缺项；通过后交付人员收到最终版本和明确实施任务。

这个场景应支持每个人选择不同的数字员工与工作方法，同时保持同一个业务实例、明确的人的职责和完整的交接证据。

| 设计选择 | 相对优势 | 代价/风险 | 优化方向 |

| 保留完整单节点执行能力 | 业务工作能留在同一上下文中完成，减少外部复制粘贴 | 功能范围大，容易变成目录拼接 | 围绕“任务—配置—执行—产物”整合；资源页面负责复用和维护 |

| B/S 与集中运行治理 | 面向企业统一交付，减少每个人安装运行时的负担 | 用户本机浏览器/桌面/文件访问需要额外桥接 | 保持网页主入口，为确需本地能力的场景提供可授权连接 |

这些是目标设计的优势与成本，不是已获得的市场优势。QoderWake 当前更值得直接学习的是资源发现、角色配置、个人执行环境、任务跟进和高级能力的入口组织；本项目的职责、权限和业务交接设计则应贯穿这些能力，而不是只作为额外的后台配置。

建议衡量：首次完成节点所需时间、无需管理员协助的配置成功率、真实业务完成率、返工率、交接等待时间、每个被接受交付物的成本。正式阈值应由真实试点建立，不能在没有运行数据时宣称提升了多少效率。
