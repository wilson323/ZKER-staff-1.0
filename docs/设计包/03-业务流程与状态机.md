# 业务流程、状态机与上下文时序

本文件定义目标业务行为。现有 Runtime 状态使用 contracts/states/runtime.yaml；新协作对象状态是候选合同；“待我处理”等界面标签只是权威事实的组合投影，不能直接写入数据库。

## 1. F01 主链：从岗位责任到下一人接手

~~~mermaid
flowchart TD
    A["发布的 SOP 版本及业务输入"] --> B["激活节点并解析人员责任"]
    B --> C{"有合格责任候选吗"}
    C -- 否 --> D["异常队列：补齐岗位或合法转派"]
    C -- 是 --> E["本人任务预览、领取或受指派"]
    E --> F["看目标、输入、交付和下一接收人"]
    F --> G{"执行方式"}
    G -- 人工 --> H["人工工作、附件与贡献"]
    G -- 数字员工或混合 --> I["选择合格 Agent 与节点配置"]
    I --> J["校验必需上下文、冻结配置与授权"]
    J --> K["DSH 实际执行，显示真实进度"]
    K --> L["候选结果与来源"]
    H --> L
    L --> M{"完成检查通过且必要审核完成"}
    M -- 否 --> N["返工、补资料或处理待确认动作"]
    N --> F
    M -- 是 --> O["责任人提交：重授权与 ResultCommit"]
    O --> P["不可变交接包及下游激活事件"]
    P --> Q["下游重授权、校验必需输入并接手"]
~~~

入口：SOP 发起、任务工作台、被授权的对话转任务。前置：有效 Membership、合法业务资源、已发布版本及明确责任候选。结束：交接包和实际下游工作关联可回读；不以 Runtime 结束或通知送达为结束。

## 2. F02 同节点多人分别带数字员工协作

~~~mermaid
sequenceDiagram
    actor A as 主执行人
    participant CP as 控制面
    actor B as 协作人
    participant BA as 协作人的数字员工
    participant ST as 贡献与业务记录
    A->>CP: 提出目标、输入、交付、期限和合法协作范围
    CP->>B: 返回授权背景与协作请求
    B->>CP: 接受，或依既有规则预授权分派
    CP->>CP: 创建合法 AD_HOC 子工作与主任务关联
    B->>CP: 为自己的工作项选择合格 Agent
    CP->>BA: 独立 Assignment/Attempt 和授权上下文
    BA->>ST: 产生候选结果与可核验依据
    B->>CP: 检查并提交专业贡献
    CP->>ST: 校验当前基线、分工、权限与版本
    CP->>A: 待接受贡献及与现有结果的差异
    A->>CP: 接受、退回或要求补充
    CP->>ST: 保存决定；主节点继续独立完成检查
~~~

邀请不授权编辑对方 Agent；对方可选择自己或共享给自己的数字员工。拒绝和超时回到主任务待处理项。两个协作人同时运行时拥有不同 WorkItem 和 active Assignment。静态流程分支仍使用 SOP 节点；临时协作采用 PRD 的 D-01，不扩充第三种 WorkExecution scope。

仅提供意见或只读抄送无需创建独立 AgentAssignment。请对方代办动作时，校验现有 Delegation 的 action/resource/purpose/expiry；群聊中“帮我做”不自动产生授权。

## 3. F03 配置、冻结与运行

| 顺序 | 操作 | 守卫 | 持久结果/失败 |
|---|---|---|---|
| 1 | 打开本次配置 | 当前人员对工作项有权 | 返回锁定项、可替换项和候选解释 |
| 2 | 选择 Agent、技能、知识、连接身份和方案 | 候选交集及字段约束 | 保存本次偏好；不授予资源权限 |
| 3 | 点击开始 | 工作项版本未变、必需输入可读、健康/预算满足 | 重算有效配置及 CandidateSnapshot |
| 4 | 建立 Assignment/Attempt | 一项一个有效分配；替换使用 fence | 冻结 ExecutionSnapshot 与 ContextBinding |
| 5 | 派发 DSH | Envelope 签名/期限、任务输入和 scope 合法 | 写入并按支持的方式装载上下文 |
| 6 | 展示运行事件 | 有序、去重、可重连 | 队列、运行、等人、待审批、待查证各有真实来源 |
| 7 | 候选完成 | 产物/回执真实且可打开 | 进入业务检查；无产物不能显示已交付 |

运行中改配置默认影响下一次尝试。若 Runtime 不支持暂停、恢复或热注入，页面显示支持的替代路径：“停止受影响尝试后重新执行”。不得调用 unsupported 后显示“已恢复”。

## 4. F04 上下文生命周期与变更

~~~mermaid
sequenceDiagram
    actor U as 业务事实维护者
    participant W as 工作项与线程
    participant C as 上下文投影
    participant G as Gateway/DSH
    participant V as 完成检查与提交
    U->>W: 确认目标、约束、输入版本和完成标准
    W->>C: 工作 revision、业务序列、来源引用
    C->>C: 按接收人/Agent、用途及当前授权裁剪
    C->>G: 冻结绑定与实际可解析的输入
    G-->>C: 投递/装载证据及已应用水位
    G->>V: 带基线和证据的结果候选
    U->>W: 修改正式输入 v1 到 v2
    W->>C: 带序列与依赖的变更事件
    C->>V: 标记受影响贡献需重核
    V->>V: 比较当前责任、revision、基线、fence
    V-->>G: 旧依据拒绝作为最新提交，给出恢复入口
~~~

### 4.1 装配算法

1. 以工作项业务输入和已经确认的决定为基线，不从两段聊天分别猜测目标。
2. 解析必需目标、约束、完成条件和来源版本；按字段对每个接收者判断用途与权限。
3. 始终保留必需事实。长历史使用带来源的摘要与按需检索，不按“最新八条”截掉早期硬约束。
4. 摘要冲突时回查原文；无法确定事实的条目进入未决项，不提升为正式决定。
5. 生成 ContextManifest，并用 ContextBinding 关联 Assignment、Attempt、ExecutionSnapshot 与基线。
6. 在唯一 DSH 边界按真实支持的装载方式交付；物化文件只产生 prepared/delivered 级证据。
7. 暴露公开的任务理解摘要、引用与输出检查，验证关键输入是否影响实际行为。
8. 在使用点、外部动作和提交点按当前授权重新判定；快照不冻结未来权限。

### 4.2 变更分级与最小影响

| 变更 | 处理 | 对当前尝试/贡献的影响 |
|---|---|---|
| 普通聊天或表达偏好 | 追加线程、按需纳入下一轮 | 不强制所有任务失效 |
| 必需输入的版本改变 | 计算引用依赖，发布新基线 | 依赖该输入的结果待重核 |
| 已确认业务事实被纠正 | 新 HUMAN_CORRECTION / DECISION 事实 | 失效旧摘要和依赖结果，保留历史 |
| 节点完成标准/范围改变 | 仅有权主体经合同允许修改 | 重新计算完成检查和受影响任务 |
| 人员转派或撤权 | 当前权利立即重判 | 阻止旧执行权未来读取/写入/提交 |
| 上下文过期 | 重新生成授权投影与绑定 | 旧投影不能被重复使用 |
| 非必需来源临时不可达 | 声明降级及影响 | 自由咨询可继续；关键业务输入不可降级成空 |
| 外部副作用结果不明 | 先查询回执/目标状态 | 不重跑整个步骤制造重复动作 |

业务 revision 与线程 sequence 不等价：聊天新增序列不必使业务 revision 改变。需要哪些事实的工作依赖记录在 sourceRefs/requiredFactKeys。ContextApplication 已观察水位和已应用水位分别维护，不要求未授权消息的原文被消费者接收。序列有裁剪缺口时，服务端提供获准的覆盖范围/检查点，客户端不能把权限裁剪误判为丢消息并枚举隐藏内容。

### 4.3 上下文读模型状态（候选）

~~~mermaid
stateDiagram-v2
    [*] --> prepared
    prepared --> delivered: 投递证据
    delivered --> loaded: 契约要求的实际装载证据
    loaded --> update_required: 相关事实改变
    prepared --> blocked: 缺必需输入
    delivered --> blocked: 无法装载
    update_required --> prepared: 新绑定或受支持的更新
    blocked --> prepared: 补齐并重授权
    prepared --> revoked: 授权撤销
    delivered --> revoked: 授权撤销
    loaded --> revoked: 授权撤销
    update_required --> revoked: 授权撤销
~~~

图中 update_required/blocked 回到 prepared 指向新绑定的投影，不修改旧不可变 Binding。撤权后可由新的合法授权产生新绑定，不能把旧 revoked 记录改回 loaded。

## 5. F05 贡献、合并与提交

~~~mermaid
stateDiagram-v2
    [*] --> draft
    draft --> submitted: 专业承担人确认并校验
    submitted --> accepted: 有权汇总者接受
    submitted --> returned: 退回并指出差异
    accepted --> needs_recheck: 所依赖业务事实改变
    returned --> superseded: 新贡献版本提交
    needs_recheck --> superseded: 新版本通过重核
    accepted --> superseded: 被已接受的新版本替代
    draft --> withdrawn: 合法撤回
    submitted --> withdrawn: 合法撤回
~~~

returned/needs_recheck 的内容不原位修改；修订创建新 contributionVersion，旧版指向替代关系。结构化字段由有权维护者确认，文件并发采用隔离候选和显式 Diff/合并，不以最后写入覆盖。

主提交条件：当前人员执行/提交权成立；当前 Assignment 和 fence 成立；所有必需输入和接受贡献仍适用；CompletionCheckResult.passed 且 expectedWorkItemRevision 与当前一致；必要审批未过期且绑定精确影响；产物可解析；外部不确定效果和关键补偿义务按合同处理。提交幂等键的相同请求返回同一结果，不同请求体冲突不能被当作重复成功。

## 6. F06 交接、接收与返工

正式 ResultCommit → 不可变 HandoffPackage → Outbox 事件 → 下游激活/接收工作 → 根据实际接收人及 Agent 重新生成投影 → 检查必需文件/结构化输出/未决项 → 接手。

需要区别：包已形成、通知已送达、人已查看、必需输入可读、下游已接手、下一节点执行中。前四项不自动意味着后两项。当前 Schema 的 targetNodeId 不能用于任意同节点共享；同节点协作通过新绑定的 sourceWorkItem/targetWorkItem 关系和正式合同扩展处理，不伪造目标节点。

返工回原责任范围，保留旧包；新增包用新版本和替代关系。已交接后发现迟到贡献，进入补充/返工流程，不能静默修改历史包或下一节点输入。

## 7. F07–F12 全域流程

| 流程 | 正常路径 | 失败/恢复 | 责任与业务结束点 |
|---|---|---|---|
| F07 转派/离岗/撤权 | 影响预览 → 合法交接 → 新人接收 → 旧权失效 → 新资格/上下文 | 无接收人产生异常待办；外部撤权失败进入调和 | HR/身份/责任人各按原授权履职；不等于一键授予所有资源 |
| F08 资源生命周期 | 创建草稿 → 校验 → 隔离试验 → 提交评审 → 发布 → 节点选择 → 使用反馈 → 升级/退役 | 缺依赖、评测失败、授权不足、版本回退 | 维护者与批准者分离；测试/目录展示不等于正式可用 |
| F09 连接器/文件/外部动作 | 接入 → 授权身份 → Grant → 节点可用 → 影响预览 → 必要确认 → 调用 → 回执 | 到期重授权；未知结果先查证；设备离线/越界拒绝 | 执行人看到以谁的账号操作；成功以真实目标及回执证明 |
| F10 自动化/IM | 配置作用域与触发 → 身份映射 → 去重 → 当前授权 → 同一工作命令 → 进度与通知 | 失效暂停、重连补投、错过触发按策略补跑 | 自动触发不绕过责任、授权和完成条件 |
| F11 SOP 设计发布 | 编辑节点合同 → 人员/资料/能力预检 → 员工预览 → Diff → 评审 → 发布新版本 | 无候选/断路/无出口/无限循环定位到节点 | 设计者不直接改在途实例，不以画布展示代替运行定义 |
| F12 治理与运行 | 管理员领域配置 → 影响评估 → 当前策略授权 → 执行 → 审计/用量投影 | 健康故障、额度、备份恢复、版本兼容、撤权调和 | 运行维护不取代业务验收；审计视图只读裁剪 |

## 8. UI 状态映射与事件合同

| 用户文案 | 权威来源 | 不允许据此推出 |
|---|---|---|
| 待领取 | 合格 HumanTask 且未被领取 | 任意人可抢占 |
| 待我处理 | assigned task / unresolved item / 当前用户决定请求 | 整个租户的待处理数量 |
| AI 执行中 | Run=queued/running 等实际状态 | 节点已开始不可撤回或已完成 |
| 等待补充 / 等待审批 | Run awaiting_input/awaiting_approval 或正式待办 | Runtime 一定支持热恢复 |
| 执行结果待确认 | reconciling / 外部结果不明事实 | 可以无条件重试 |
| 待合并贡献 | Contribution=submitted | 贡献已成为正式共同事实 |
| 待重核 | 依赖变化及 needs_recheck | 整个项目必须停止 |
| 已交付 | 当前工作提交事实和合法业务终态 | 下游已阅读或已执行 |

现有 Run 合同：queued → running/cancelled；running → awaiting_input/awaiting_approval/reconciling/succeeded/failed/cancelled；awaiting_input → running/cancelled；awaiting_approval → running/failed/cancelled；reconciling → succeeded/failed。支持状态转换的合同不等于 Adapter 已实现对应操作，按钮仍须依据真实 capability availability。

建议业务事件逻辑信封：eventId、tenantId、aggregateType/id、sequence、revision、occurredAt、causationId、correlationId、payloadRef/digest、classification。这是现有事件/Outbox 的扩展需求，不新建平行总线。重复事件去重，乱序按聚合序列补取，gap 后从权威读模型恢复；客户端断线不导致重复执行业务。

## 9. 负面情景要求

所有流程都必须覆盖：未登录、越权/不存在、工作 revision 冲突、人员/资源被撤销、资料缺失、网络断线、双击/重投、外部结果不明、无产物、过期审批、旧 Agent 迟到提交、下游无法读取。错误保留用户草稿和原任务定位；没有额外权限时不显示越权对象的细节或数量。


## 10. F13 员工从市场复制并用于本人工作

~~~mermaid
flowchart TD
    A["员工工作区或节点配置"] --> B["按权限浏览数字员工、技能和工具"]
    B --> C["读取来源、版本、用途及允许采用方式"]
    C --> D["点击复制并使用；使用点重新校验"]
    D --> E["按类型创建个人副本与来源记录"]
    E --> F{"当前权限、发布、依赖与节点要求齐备"}
    F -- 是 --> G["加入我的资源，回本人节点选中"]
    F -- 否 --> H["保留副本，显示待配置、授权、发布或兼容问题"]
    H --> F
    G --> I["复用配置、独立Assignment与上下文执行链"]
~~~

市场可见不代表可复制；副本形成不代表节点已可执行。幂等重试查同一采用结果，显式再复制创建新意图。无需把每次获准复制都转为人工审批；已有权限和发布要求仍在使用点校验。复制不带原作者凭据、私人资料或源维护权。详见 [员工市场复制与使用设计](<12-员工市场复制与使用设计.md>)。

## 14. 同日多次发起与跨流程统一办理（v2.5）

OA补充设计给出多次发起的时序、跨节点独立审核/退回、依据变更使旧审批失效、领取竞争、催办、抄送、撤回和外部效果补偿规则。并行实例与实例内并行审批是两个维度。任务“我已处理”、审批决定、阅读状态和实例完成分别记录；同一模板的其他实例不因某一笔操作而改变。新一轮人员任务与审批保留旧记录，不能复用旧回执。
