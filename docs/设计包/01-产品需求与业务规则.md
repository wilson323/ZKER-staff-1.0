# ZKER-staff 产品需求与业务规则

版本：设计包 v2.2｜2026-09-11｜基于源码 21a230f2c7a6a26e68a5eff1c36788d6f4206eab  
性质：本次优化的完整设计提案，补充既有产品基线；不替代仓内 SSOT，不表示所述能力已实现或发布。全部 153 项见 [06-用户故事与153项追踪矩阵.md](<06-用户故事与153项追踪矩阵.md>)。

## 1. 产品定义与目标

ZKER-staff 面向企业跨岗位业务协作。SOP 把工作与人串联起来，每个人看到自己的职责、输入、交付标准和下一接收人，在获准的范围内选择自己的或共享的数字员工、技能、知识、连接身份和执行方案。数字员工负责授权内执行；人类保留责任、专业确认和独立审批职责。

QoderWake 对标价值主要落在节点内数字员工工作环境：能力发现、配置、对话、工作空间、工具连接、定时和执行反馈。完整竞品差异、已观察功能与未验证项保留在优化清单。这里将这些能力嵌入人的工作节点，并补上多人责任、版本化上下文、业务完成和跨人交接。

衡量价值的单位是“有责任归属且通过验收的业务交付”，而非聊天数、工具安装数或 Agent 运行数。

### 1.1 面向用户的问题与成果

| 用户问题 | 目标体验 | 可验证成果 |
|---|---|---|
| 不知道为什么轮到我 | 任务卡直接显示岗位解析、本人分工、期限和上下游 | 用户可从工作台进入正确待办并说明职责 |
| 会聊天但没法完成节点 | 在节点配置资源、执行、修改、检查、提交 | 一个 WorkItem 关联完整配置和交付证据 |
| 需要其他人及其 AI 协助 | 邀请明确分工；协作人各自选 Agent；汇总贡献 | 两人独立运行不覆盖彼此分配，主任务统一验收 |
| 人与 AI 使用不同版本资料 | 共同业务基线、按接收者投影、变更影响与旧结果拦截 | 输入变更后受影响贡献被识别并重核 |
| 管理端复杂，普通员工也被迫填写技术字段 | 员工按业务选择；维护者管理版本与连接；管理员治理边界 | 员工不需填写 UUID、Manifest、Secret 或协议 JSON |
| 流程提交后下游仍要追问 | 不可变交接包、必需输入可读性检查和接收确认 | 下游无需复制聊天，能从被授权交付继续执行 |

### 1.2 产品边界

商业闭源 B/S，使用已有租户、组织和会话体系；不设计自助开户漏斗。Python/FastAPI 控制面、React/TypeScript Web、PostgreSQL 写模型、S3 兼容对象存储和既有 Runtime Gateway/DSH 边界保持一致。员工使用租户允许的模型配置，不新增员工级模型供应商体系。

完整平台设计保留 Team、A2A、设备桥接、Memory/Evolution、Channel/Open API 等能力。未通过既有租户启用和发布认证的能力保持条件可用，不能因为出现在本包就成为默认菜单或首发承诺。原型中的团队、连接和运行数据均为演示。

### 1.3 员工侧资源市场

员工可从工作区、节点配置和资源目录进入市场，按权限查看数字员工、技能和工具，复制到自己的资源后直接选用。已获准、已发布且依赖齐备的资源无需重复申请权限；需要本人连接身份或其他条件时显示准确缺项。复制保留来源与版本，私人记忆、对话、文件、凭据和源维护权不会随复制传递。详细复制语义、权限、UI和验收见 [员工市场复制与使用设计](<12-员工市场复制与使用设计.md>)。

## 2. 角色、关系与责任

| 业务角色 | 主要目标 | 授权内动作 | 责任边界 |
|---|---|---|---|
| 节点责任人 | 保证节点交付 | 分派、处理异常、确认完成、组织返工 | 责任视图；不直接推导平台角色权限 |
| 主执行人 | 完成主要任务并汇总 | 领取、选 Agent、组织协作、修改、提交候选 | 不能改变他人私人资源或代替独立审批 |
| 协作人 | 完成专业分工 | 接受分工、独立配置、提交贡献、响应返工 | 只在协作工作范围内执行 |
| 写作人 | 编写报告、材料或方案 | 作为主执行人或协作人撰写、引用、修订 | “写作”是业务分工，不新增系统身份角色 |
| 数字员工使用者 | 使用合格数字员工完成工作 | 选择、调用、查看授权内历史 | 使用、编辑、发布、共享四种权利分别判断 |
| 数字员工/资源维护者 | 提供可靠版本 | 草稿、试验、提交发布、影响分析 | 维护资源不意味着读取全部使用者任务 |
| 审核/审批人 | 专业审核或批准受控动作 | 在 assigned request 范围内决定 | 专家咨询、已读、AI 建议均不是审批回执 |
| 流程设计者 | 定义跨岗位业务链 | 设计节点、预检、评审、发布新版本 | 在途实例保持原版本，变更需影响分析 |
| 管理/审计/运维角色 | 各自领域管理 | 使用现有七类 canonical 夹具及精确角色合同 | 没有通用 ADMIN，也不默认读取私人对话 |

资产归属、资源使用权、当次分工和最终业务责任是四条关系。共享数字员工不复制原作者的连接身份、私有记忆、私人草稿或管理权。人类当前责任使用 HumanTask.claimant；禁止新增第二份可独立修改的“主执行人表”。

v2.4 将上述责任概述展开为 [15-全角色界面与操作覆盖矩阵.md](<15-全角色界面与操作覆盖矩阵.md>) 中的41个业务视角、全部44个人类角色键及服务身份边界。每个视角具有明确页面、可见范围、主操作和禁止操作；七类登录夹具不作权限继承。原有153项需求口径保持不变。

## 3. 统一业务对象与产品层次

1. 企业流程：SOPVersion / ProcessInstance 决定节点激活、分支、等待、返工和业务完成。
2. 人的工作：WorkExecution / WorkItem / HumanTask 承载责任与交付。
3. 数字员工分配：CandidateSnapshot → AgentAssignment → ExecutionAttempt，记录本次选择与有效配置。
4. 节点内执行：DSH 内部技能、子智能体或执行方案，生成结果候选；不能自行推动企业下一节点。
5. 协作与交接：WorkThread、ContextManifest、CompletionCheckResult、ResultCommit 和 HandoffPackage。

**新增设计选择 D-01：** 对临时出现、需要独立数字员工运行的协作分工，建议以既有 AD_HOC 创建命令建立独立合法工作执行及工作项，再用 CollaborationLink 关联主 WorkItem。子任务的 IntentDecision 明确记录“协作请求”来源与业务资源；不能伪装成主流程中新激活的 PROCESS 节点。流程模板中预先可知、决定企业路径的分工，应继续建成 SOP 子节点/子流程。二者在主节点协作视图汇合，但状态与作用域分别保留。

该关联尚需合同和消费者实现；没有宣称代码已支持。采用此方案保留每个 WorkItem 仅一个 active AgentAssignment 的数据库约束。多人参与而不需要独立 AI 运行时，使用已有线程、HumanTask/有界 Delegation，不为每句聊天创建子任务。

## 5. 关键业务规则

| 规则 | 明确行为 | 失败时 |
|---|---|---|
| BR-01 责任 | 领取只改变人员责任，不自动选 Agent 或启动 | 并发领取失败返回当前归属，不静默抢占 |
| BR-02 资格 | 可选集合为节点要求、已发布版本、当前使用权、健康、预算和政策的交集 | 列出本人可见的不可用原因；不泄漏无权对象 |
| BR-03 配置 | 有效配置按组织政策 → 节点必需项 → 合法个人选择解析；冻结执行版本 | 必需项不满足时阻止相关执行 |
| BR-04 单一分配 | 一个 WorkItem 只有一个有效 AgentAssignment，改派创建新尝试 | 旧分配和迟到尝试不能提交 |
| BR-05 协作责任 | 主任务提要求，协作人对专业贡献负责，主执行人汇总 | 拒绝、超时、人员离岗产生可处理工作 |
| BR-06 共同事实 | 所有人引用相同已确认业务版本；可见字段按接收者不同 | 缺必需共享事实时标明缺项，不能由 Agent 猜测 |
| BR-07 信息共享 | 只读抄送不产生动作授权；代办复用有界 Delegation | 无合法执行权则只允许阅读获准投影 |
| BR-08 上下文装载 | 区分已生成、已送达、实际装载证据、公开理解检查 | 无真实装载证据不显示“AI 已掌握” |
| BR-09 变更影响 | 重要输入/正式决定变更只影响依赖者；撤权即时重新判定 | 相关贡献待重核，普通闲聊不全局停工 |
| BR-10 成果 | 数字员工仅产出候选；必需检查、责任确认及必要审批满足后提交 | 无产物、检查失败、审批过期均不能完成 |
| BR-11 提交 | 提交绑定工作项 revision、Assignment、fence、输入基线和幂等键 | 旧版本冲突返回可恢复差异，不覆写最新结果 |
| BR-12 外部动作 | 调用身份、目标、范围和风险可解释；未知结果先查证 | 不确定时保留回执，不盲目重复外部写入 |
| BR-13 交接 | 包不可变，下游按当前接收人重新授权投影并检查必需资料 | 已收到但无法读取的包不能被视为可开始执行 |
| BR-14 终态 | 技术运行、协作贡献、主节点、流程、通知各保留自身状态 | UI 只映射权威状态，不以消息“完成”推断业务终态 |
| BR-15 保留 | 历史版本和证据按既有保留政策处理；当前权利在每次读取重查 | 归档不等于删除；撤权不伪造历史未发生 |
| BR-16 能力可用性 | 产品设计存在、租户启用、发布认证分开显示 | 条件能力不默认进入普通用户正式入口 |

## 6. 配置产品设计

本次配置表单包括执行模式、数字员工、技能与参数、必需/追加知识、连接器动作和身份、工作空间及读写范围、执行方案、预算继承、结果格式、个人补充说明。字段有“节点锁定、可替换、可追加、不可用”四种解释，不能仅以 disabled 按钮呈现原因。

保存范围默认“仅本次节点”；明确选择后才存个人偏好；共享模板只生成变更提案。预览展示差异与真实继承来源。开始执行前服务端重算资格、生成快照并引用其 digest；运行中不能悄悄替换快照。纯人工路径不要求 Agent 凭据，仍需交付和完成检查。

## 7. 代表性业务故事

企业项目“设备采购方案”中，甲为主执行人，乙负责技术清单，丙负责预算，丁为独立审核人。甲选方案数字员工，乙选技术数字员工，丙选报价数字员工。乙发布设备清单 v2 后，依赖 v1 的预算标为待重核；甲不能把旧预算作为最新结果交付。丙从 v2 的授权资料重新执行并确认新预算；甲接受贡献、汇总方案；丁完成所需审核后形成正式交接包，下一岗位按权限读取。

技术人员无需读取采购底价，预算人员无需读取技术人员私人工作笔记；双方仍对设备型号和数量使用同一已确认版本。甲看协作状态和贡献，不因此获得乙、丙数字员工的管理权限。

## 8. 成功指标与发布范围

指标定义见开发验收文档：首个合格业务交付耗时、业务完成率、人工返工率、交接等待时间、过期贡献拦截率、上下文缺失率、重复副作用次数。每项必须有事件来源、分子、分母和统计窗口。性能/业务目标阈值需基于真实试点校准；本包不编造用户数量、节省比例或上线承诺。

推荐先交付单节点完整链，再加入两人各自选 Agent 的协作闭环和跨节点交接；P1/P2 功能保留完整设计与追踪。分期是实施依赖，不删除需求、不改原优先级，也不自动把条件能力改为租户默认。


## 9. 市场采用后的个人配置边界

市场是跨资源发现与复用入口，维护端负责发布与范围，员工端负责发现、复制和本人选用。市场条目可见、可复制、可编辑、可运行与可用于当前节点分别判定。原样复制保留批准内容的版本依据并走现有合法采用/发布策略；修改派生副本产生新的验证与发布工作，不能冒用源版本的授权。

## 10. 多流程、多笔事务与成熟OA（v2.5）

一个SOP版本可以在同一天创建多个独立业务实例；每个人可以参与多种流程和多个实例，也可以在同一实例承担多个节点。首页以本人的统一待办为入口，实例、工作项、人员任务、助手分配和执行尝试保持不同对象。发起新申请与重试同一次提交有不同幂等意图，不按“模板+日期”全局去重。

## v2.6 产品主旨、B/S与字段核查

本项目是以 OA 工作流为基础的企业 B/S 协作软件：流程连接人、责任和任务，由承担人在自己的任务内配置数字员工。业务发起 → 人员待办 → 本人配置数字员工 → 执行与确认 → 审批或交接 → 下一位承担人。既有平台能力全部保留。
