# 开发启动、测试与故障恢复手册

开发文档包0.1｜当前是资料与合同工作区，`PRODUCT_NOT_CONFIGURED`。本手册区分已真实可运行的本地检查与采用底座后必须补录的产品运行步骤，避免向AI编程提供虚构启动命令。

## 1. 当前环境与来源

只读版本探测记录见[implementation-environment.json](../../validation/implementation-environment.json)。本次观察到Python 3.14.7、Node v22.22.3、npm 10.9.8、Java17、Maven3.9.11、Docker CLI29.7.2；未找到mysql客户端。可执行文件的真实路径记录在报告内，不能因命令名相同忽略宿主来源。

只验证了CLI版本输出，没有探测/启动Docker守护进程、数据库或产品服务。Java可用不代表安全补丁和候选依赖兼容已满足。仓库当前没有已选产品package/pom、迁移执行或真实登录端点，因此没有可承诺的产品build/start/stop命令。

## 2. 当前可运行的检查

工作目录必须是本项目绝对目录。下列命令不安装候选、不访问生产、不创建数据库：

```sh
cd '/Users/mac/Documents/OA数字员工协作平台'
make entry
python3 validation/check_implementation_contracts.py
make verify
```

独立合同检查器只用Python标准库，支持本包实际采用的Schema关键字；遇到未支持关键字应报错，不能默默忽略。它不等于完整OpenAPI认证或数据库解析器。其结果见[implementation-contract-check.json](../../validation/implementation-contract-check.json)。`make verify`沿用现有任务图、产品设计资料与工程工具检查；PASS仅适用于本地开发体系，不升级productReady。

只有明确修改合同后才重新生成，不要每次验证前覆盖合同以掩盖差异：

```sh
python3 validation/build_implementation_contracts.py
python3 validation/build_implementation_data.py
python3 validation/build_implementation_fixtures.py
python3 validation/build_implementation_appendices.py
python3 validation/check_implementation_contracts.py
```

生成脚本修改范围为本包派生合同/附录。先记录差异和哈希，再检查；保持30号需求与31号原型不变。尚未配置的产品验证入口应保持明确阻断，而不是添加永远返回0的脚本。

## 3. M0采用底座后的运行档案

使用原`validation/development-workflow.json`的product字段，不建第二运行状态文件。采用时逐项记录真实信息：

| 项 | 必需记录 | 取得方法 |
|---|---|---|
| 代码和模块 | repo/commit/补丁/启用模块/依赖锁 | 当前checkout与原生构建文件 |
| 工具 | 实际Java/Node/包管理器/数据库版本及路径 | `--version`与进程来源交叉核对 |
| 配置 | 配置文件路径/profile/端口/数据库schema/存储命名空间 | 读取实际选定底座；秘密只记录引用 |
| 命令 | clean build、测试、start、health、stop | 从固定版本README、pom/package和真实成功执行提取 |
| 初始化 | 合法SQL来源/哈希/迁移版本/演练环境 | 按49号先审查后隔离执行 |
| 登录 | 本地虚构成员及角色范围，实际登录方式 | 原生身份配置，不生成默认通用管理员密码 |
| 服务来源 | PID/listener/cwd/参数/profile/日志路径 | 启动后检查监听者及健康输出 |
| 回退 | 上一可用版本、配置包、备份位置及恢复验证 | 真正停启和回读数据后登记 |

只有这些信息已被真实执行证明，才能把命令加入产品检查配置。低代码导出的流程/表单/规则/插件清单同样固定版本和digest，禁止只保留设计器截图。

## 4. 本地启动顺序与停止原则

采用后顺序：检查当前目录与端口来源→选定底座原生依赖→受限测试数据库/私有对象存储→原生后端与OA→同一SDK执行服务→前端→健康检查→真实登录→M1链路。服务由原有启动机制管理，不能多起另一套身份/调度/Agent循环。

停止前记录运行中的Attempt和未知Invocation；先停止新触发，再让在途操作到检查点/查证状态，最后按实际服务管理器停止。只操作自己记录的PID/服务，不能按宽泛进程名kill相邻项目。本次没有启动产品，也没有执行stop/kill。

## 6. 故障定位与恢复

| 症状 | 先取证 | 恢复动作 | 停止条件 |
|---|---|---|---|
| 页面空白/登录失效 | 实际URL、Network状态、会话adapter、前端错误 | 重新登录或修复真实映射，保留当前任务位置 | 无会话不请求受限数据 |
| 待办消失/403 | 当前任职、OA责任、policy/authz epoch | 重取授权投影；必要时联系当前有权维护者 | 不把403映射成无任务 |
| 配置409 | 当前revision/epoch与本地base版本 | 展示差异、合并允许字段、重新保存 | 禁止覆盖他人新值 |
| 执行停滞 | Attempt、SDK run/checkpoint、fence、工具回执 | 有检查点才恢复；未知效果先C14 | 无回执不得新发外部写 |
| 交付待同步 | operation/delivery/outbox/inbox、OA实例节点 | 查证原业务键，补记真实确认 | 不手改WorkItem为COMMITTED |
| 知识无结果 | 实际摄取/解析/索引/授权/来源版本 | 先修来源和任务状态再重处理 | 无数据不返回假引用 |
| 插件停用后任务失败 | 固定版本、依赖图、授权变化 | 回兼容版本或经有权人员切人工任务 | 安全撤权不能用旧版本绕过 |
| AI预算耗尽 | token/工具次数/耗时与已计量事件 | 停止当前循环，返回候选和人工接管 | 不自动换账号或规避限额 |

恢复权限与常规权限一样细分；运维能看脱敏运行关联不等于能读业务文件。日志不保存完整prompt、凭据、原始私有知识或真实个人数据。
